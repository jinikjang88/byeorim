# ADR 0012. Shape 단계 책임과 architecture.yml 형식

- 상태: 채택
- 날짜: 2026-04-28
- 결정자: DevSmith

## 맥락

ADR 0007이 `.byeorim/project/architecture.yml`을 Shape 단계 산출물 자리로 박았다. 그러나 그 파일 안이 어떻게 생겼는지, Shape이 어떤 결정을 책임지는지는 정하지 않았다. 이 ADR이 그 자리를 채운다.

Shape는 "쇳물을 거푸집에 부어 형태를 잡는 일"이다(MANIFESTO III장). 직전 단계(Smelt)가 정한 블럭과 의존성을 입력으로 받아, 그 블럭들이 어떤 기술적 형태를 가질지 결정한다. 데이터베이스, 언어, API 형식, 구조 패턴 같은 자리.

답해야 할 질문은 다음 셋이다.

첫째, Shape가 책임지는 결정 영역이 무엇인가. 너무 좁으면 다음 단계(Forge)가 정해야 할 자리가 모호해지고, 너무 넓으면 사용자가 첫 만남에서 압도된다.

둘째, architecture.yml의 형식이 어떻게 생겼나. ADR 0008이 intent.yml에 한 결과처럼 schema_version과 미래 마이그레이션 자리가 필요하다. 결정 자체는 자유 텍스트가 아니라 정해진 옵션 중 하나여야 다음 단계(Forge)가 그 위에 코드 생성을 올릴 수 있다.

셋째, decisions.yml의 cascade 답안을 이 단계에서 어떻게 활용하나. Smelt가 모은 cascade 결정에 사용자가 답을 채웠다면, 그 답이 Shape의 결정에 영향을 준다. "정산 주기 D+1"은 배치 잡 빈도를 정하고, "쿠폰 비용 플랫폼 부담"은 정산 로직 형태를 정한다. 다만 이 영향을 알고리즘적으로 자동화할지, 사용자에게 맥락만 보여줄지 결정이 필요하다.

넷째, 결정마다 ADR을 자동 생성할지. CLAUDE.md 섹션 6은 아키텍처 결정에 ADR을 요구한다. Shape가 만드는 결정이 그 약속을 어떻게 지킬지 정해야 한다.

## 검토한 옵션

### 결정 1. Shape가 책임지는 결정 영역

#### 옵션 A. 4개 핵심 자리: 언어, 저장소, API 형식, 구조 패턴
- 장점: 비기술 창업자도 한 번에 다 답할 수 있는 양. 이 4개가 정해지면 Forge가 시작할 수 있는 최소 형태가 된다. 다음 출시에서 추가 자리(인증, 캐시, 메시지 큐)는 별도 ADR로 추가
- 단점: 처음에 한정된 자리만 다룬다. 시니어 개발자(우선순위 3번)는 더 깊은 결정을 직접 하고 싶을 수 있음

#### 옵션 B. 깊은 결정 셋(8~12개)
- 장점: 결정 깊이가 깊다
- 단점: 비기술 창업자(우선순위 1번)에게 압도적. CLAUDE.md 섹션 0의 사용자 우선순위 1번 위배

#### 옵션 C. 최소 1~2개(언어만)
- 장점: 가벼움
- 단점: Forge가 시작하기에 정보가 부족. 결국 Forge가 빠진 자리를 묻게 되므로 Shape의 의미가 약해진다

### 결정 2. architecture.yml 형식

#### 옵션 A. 평면 키-값(language, database, api_style, architecture_pattern)
- 장점: 단순하다. 다음 단계가 한 자리만 보면 된다
- 단점: 결정에 부연 설명(rationale)을 붙일 자리가 없다. 미래에 ADR 생성 시 부연이 필요해질 수 있음

#### 옵션 B. 구조화된 결정 객체(`decisions: { language: { value, rationale } }`)
- 장점: rationale 같은 부연을 붙일 자리가 미리 있음
- 단점: 처음에는 rationale이 비어있어 형식이 무거워 보임

#### 옵션 C. 결정 배열(`decisions: [{ key, value }, ...]`)
- 장점: 결정 추가가 자연스러움
- 단점: 다음 단계가 키 검색을 해야 함. 평면 키-값보다 사용이 번거롭다

### 결정 3. cascade 답안 활용 방식

#### 옵션 A. 맥락만 보여주고 직접 참조하지 않는다(이번 출시)
- 장점: Shape 코드가 단순하다. 답안이 사용자 머릿속의 맥락이 되어 결정에 자연스럽게 반영
- 단점: 자동화의 이점이 없다. 답한 내용이 어떻게 Shape 결정에 영향을 줬는지 추적이 약함

#### 옵션 B. cascade 답안을 알고리즘적으로 매핑(예: "정산 주기 D+1" → 배치 잡 설정)
- 장점: 답안이 결정에 직접 반영됨
- 단점: 매핑 규칙이 복잡하고 도메인별로 다르다. MVP에서 짤 수 없음. 잘못된 매핑은 사용자를 잘못된 자리로 이끔

#### 옵션 C. 답안을 architecture.yml에 그대로 복사
- 장점: 추적이 명확
- 단점: 데이터 중복(decisions.yml에 이미 있음)

### 결정 4. 결정마다 ADR 자동 생성

#### 옵션 A. 자동 생성 안 함, architecture.yml에만 기록(이번 출시)
- 장점: 단순하다. ADR 자동 생성은 본문 자체가 만만찮은 자리(왜 그 결정을 했는지의 자유 텍스트). 잘못 자동화하면 가짜 ADR이 양산됨
- 단점: CLAUDE.md 섹션 6이 요구하는 "아키텍처 결정에 ADR"을 코드가 자동으로 만들어주지 않음

#### 옵션 B. 자동으로 ADR 파일 생성(템플릿 기반)
- 장점: 형식 일관성
- 단점: 템플릿 채우기가 자동화되더라도 "왜 이 결정을 했는가"의 맥락은 사람이 채워야 함. 그 자리가 비어있는 ADR은 죽은 문서

#### 옵션 C. 부분 자동: ADR 빈 템플릿만 만들고 사용자가 채움
- 장점: 형식 부담 줄임 + 맥락은 사람이
- 단점: 빈 ADR이 쌓이면 노이즈. 채우지 않은 ADR은 가치가 없다

## 결정

### 결정 1: 4개 핵심 자리 (옵션 A)

이번 출시의 Shape는 다음 4개 결정만 다룬다.

- `language`: 어떤 언어/런타임으로 만들 것인가. 옵션은 `node`, `java`, `python`
- `database`: 데이터를 어디에 저장할 것인가. 옵션은 `postgresql`, `mysql`, `sqlite`, `mongodb`
- `api_style`: API의 형태. 옵션은 `rest`, `graphql`, `rpc`
- `architecture_pattern`: 코드 구조. 옵션은 `monolith`, `modular-monolith`, `microservices`

이 4개는 Forge가 시작할 수 있는 최소 형태다. 추가 결정(인증 방식, 캐시 전략, 메시지 큐)은 미래 출시에서 별도 ADR로 추가한다.

각 옵션 값(소문자 식별자)은 표준이다. 사용자에게 보일 때는 한국어 안내가 함께 나간다(예: "Node.js (JavaScript/TypeScript)").

### 결정 2: 평면 키-값 (옵션 A)

architecture.yml은 다음 형식이다.

```yaml
schema_version: 1
created_at: 2026-04-28T...
language: node
database: postgresql
api_style: rest
architecture_pattern: modular-monolith
```

평면 키-값으로 충분하다. rationale 같은 부연이 필요해지면 schema_version 2로 올리고 마이그레이션 결정을 별도 ADR로 한다.

### 결정 3: 맥락만 보여주고 직접 참조하지 않는다 (옵션 A)

interactiveShape는 decisions.yml을 읽어 답한 결정 수와 빈 결정 수를 사용자에게 안내 메시지로 보여준다(또는 askArchitecture에 context로 전달). 답안 내용을 architecture.yml에 복사하거나 알고리즘적으로 매핑하지 않는다.

답안의 영향은 사용자 머릿속에서 일어난다. "쿠폰 정산이 D+1이라면 데이터베이스 선택은 어떨까" 같은 사고가 사용자 내면에서 자연스럽게 이루어진다. 자동화는 매핑이 무르익으면(미래 출시) 별도 ADR로 도입한다.

### 결정 4: 자동 ADR 생성 안 함 (옵션 A)

Shape는 architecture.yml에 결정만 기록한다. ADR 파일을 자동으로 만들지 않는다.

CLAUDE.md 섹션 6의 약속(아키텍처 결정에 ADR)은 사용자가 직접 ADR을 작성하거나, 미래의 별도 명령어(`byeorim decide`나 `byeorim adr` 같은 자리)가 architecture.yml의 결정을 토대로 ADR 빈 템플릿을 만드는 흐름으로 지킬 수 있다.

이번 출시는 ADR 자동 생성을 하지 않으므로, 사용자가 architecture.yml의 결정을 ADR로 옮기는 일은 수동이다. 다만 architecture.yml 자체가 결정의 단일 출처이므로 추적이 어렵지 않다.

## 결과

### 긍정적
- 비기술 창업자가 4개 결정만 답하면 다음 단계로 갈 수 있다. 1순위 사용자 우선순위가 형식에 박혔다
- 평면 키-값 architecture.yml은 다음 단계(Forge)가 그 위에 코드 생성 로직을 올리기 쉬운 형태다
- cascade 답안을 알고리즘적으로 매핑하지 않아서 잘못된 자동화로 사용자를 잘못된 자리로 이끌 위험이 없다. 답안의 영향은 사용자가 직접 본다
- ADR 자동 생성을 안 해서 가짜 ADR이 쌓이지 않는다. ADR은 사람이 의도를 담아 쓰는 문서라는 정신을 보존
- 4개 결정의 옵션 값(소문자 식별자)이 표준이라 미래의 어댑터(예: 코드 생성기)가 분기점으로 사용할 수 있다

### 부정적 / 트레이드오프
- 4개 결정만으로 Forge가 시작하기에 정보가 모자랄 수 있다. Forge가 자체적으로 묻는 자리가 생긴다면 Shape를 확장하거나 Forge에 그 자리를 둔다(별도 ADR)
- 시니어 개발자(우선순위 3번)는 더 깊은 결정을 직접 하고 싶을 수 있다. 이번 출시는 평균 사용자에 맞췄고, 시니어 사용자는 architecture.yml을 직접 편집해 추가 필드를 넣을 수 있다(다만 그 필드는 다음 단계가 모른다)
- cascade 답안을 직접 활용하지 않으면 답한 내용이 architecture에 어떻게 반영됐는지 명시적 추적이 약하다. 미래 출시에서 매핑 규칙이 ADR로 들어오면 강해진다
- 자동 ADR 생성이 없으므로 사용자가 ADR을 안 쓰는 자리가 생긴다. CLAUDE.md 섹션 6의 약속은 코드 강제가 아니라 정책 강제로 남는다

### 미래 묶임
- 4개 결정 키(language, database, api_style, architecture_pattern)와 각 옵션의 소문자 식별자는 표준이다. 새 옵션을 추가하거나 키를 바꾸려면 ADR이 필요하다
- architecture.yml의 평면 형식은 schema_version 1의 표준이다. 변경하려면 schema_version 2로 올리고 마이그레이션 ADR이 필요하다
- 추가 결정 자리(인증, 캐시, 큐 등)는 별도 ADR로 추가한다. 한 번에 묶어 추가하지 않고 자리마다 결정 근거를 따로 박는다
- cascade 답안의 알고리즘적 매핑은 미래 ADR로 도입한다. 이번 결정은 그 자리를 비워둔 상태
- 자동 ADR 생성은 미래 ADR로 결정한다. 도입 시 빈 템플릿이 양산되지 않는 매커니즘(예: 사용자가 ADR 작성 시작 시점에 명시적 호출)이 함께 와야 한다
