# ADR 0017. 생성 코드 7대 원칙 (메타)

- 상태: 채택
- 날짜: 2026-04-28
- 결정자: DevSmith

## 맥락

ADR 0015가 set 단계의 MVP를 합성 README로 정하면서 실제 코드 생성을 미래 ADR로 미뤘다. 그 자리를 채우려면 두 종류의 ADR이 필요하다.

첫째, 생성 코드의 보편 원칙. 어떤 언어로 생성하든 이 원칙은 흔들리지 않아야 한다. 보안, 모듈 분리, 컨벤션, 의존성 방향, 유지보수, BE/FE 분리, 디자인 패턴 같은 자리.

둘째, 언어별 구체 결정. Node/Java/Python 각각의 프레임워크, 빌드 도구, 디렉토리 구조 같은 자리.

이번 ADR은 첫째 자리를 박는다. 7개 원칙을 표준으로 정하고, 미래의 언어별 ADR(0018 Node, 0019 Java, 0020 Python, 그 이후)이 이 7원칙을 어떻게 실천하는지 명시하도록 강제한다.

7개 원칙은 사용자가 직접 정한 자리다. 벼림의 1순위 사용자(비기술 창업자)가 만들어낸 코드를 6개월/1년 뒤에 이어받을 다음 사람(개발자, AI 도우미)이 읽고 고칠 수 있어야 한다는 정신에서 나온 자리.

## 검토한 옵션

이 ADR은 7개 결정을 다룬다. 각 결정마다 "이 원칙을 보편 원칙으로 둘 것인가, 언어별 ADR로 미룰 것인가" 두 옵션을 본다.

### 결정 1. 보안 최고 우선순위

#### 옵션 A. 메타 ADR이 보안을 최우선 원칙으로 박음
- 장점: 모든 언어 ADR이 보안 자리를 처음부터 챙긴다. 미래에 새 언어가 들어올 때도 보안이 첫 결정이 됨
- 단점: 각 언어의 보안 기본값이 다르므로 메타 ADR은 추상적 원칙만 정함. 구체는 언어별 ADR

#### 옵션 B. 언어별 ADR이 보안을 알아서 다룸
- 장점: 언어별 자유도
- 단점: 보안이 후순위로 밀릴 위험. 한 언어에서 빠뜨린 자리가 다른 언어로 전염

### 결정 2. MSA 준비를 위한 기능 분리와 멀티모듈

#### 옵션 A. 메타 ADR이 "feature 단위 모듈 분리"를 표준으로
- 장점: 모든 언어에서 같은 결로 모듈을 나눈다. 미래 MSA 분리 시 한 단위(feature)가 한 서비스로 빠지는 흐름이 일관됨
- 단점: 언어마다 모듈 시스템이 달라(Java multi-module Gradle, Node workspaces, Python packages) 메타 ADR은 의도만, 구현은 언어별

#### 옵션 B. 언어별 ADR이 자체 모듈 시스템 결정
- 장점: 자유도
- 단점: 한 언어는 layered, 다른 언어는 feature-based가 되면 6개월 뒤 사용자가 헷갈린다. 언어를 바꾸려는 사람이 두 결을 새로 배워야 함

### 결정 3. 일관된 코드 컨벤션

#### 옵션 A. 언어별 표준 컨벤션을 그대로 따름 (메타 ADR이 "표준 따른다"를 박음)
- 장점: Node는 ESLint+Prettier 표준, Java는 Google Java Style 또는 Spring 표준, Python은 PEP 8 같은 자리. 각 언어 커뮤니티가 모이는 자리를 그대로 사용
- 단점: 언어 간 비교가 어려워질 수 있음(예: snake_case vs camelCase)

#### 옵션 B. 벼림 자체 컨벤션 표
- 장점: 언어를 가로지르는 일관성
- 단점: 각 언어 커뮤니티의 표준과 충돌. 외부 도구가 우리 컨벤션을 모름

### 결정 4. 의존성 단방향 또는 일관된 의존성 참조

#### 옵션 A. 메타 ADR이 단방향 의존성 그래프를 표준으로
- 장점: CLAUDE.md 섹션 3이 벼림 자체 코드(packages/core ← catalog ← cli)에 박은 의존성 방향 정신을 생성 코드에도 적용. domain 레이어는 infrastructure를 모르고, infrastructure는 web을 모름 같은 자리
- 단점: 언어별로 의존성 방향을 강제하는 도구가 다름(Java는 archunit, Node는 eslint-plugin-import, Python은 import-linter). 메타 ADR은 의도만, 구현은 언어별

#### 옵션 B. 언어별 ADR이 자체 결정
- 장점: 자유도
- 단점: 한 언어는 단방향, 다른 언어는 자유 의존성이 되면 일관성 깨짐

### 결정 5. 유지보수 우선

#### 옵션 A. 메타 ADR이 "영리한 코드보다 읽기 쉬운 코드"를 박음
- 장점: 모든 언어 ADR이 가독성을 최우선으로 둠. 함수가 짧고 한 가지 일만 함, 변수 이름이 자기 설명적, 주석이 WHY를 다룸 같은 자리
- 단점: "유지보수"가 추상적이라 구체적 검증이 어려움

#### 옵션 B. 메타 ADR이 정량 지표(함수 길이 N줄 이하, 순환 복잡도 M 이하)를 박음
- 장점: 검증 가능
- 단점: 정량이 언어/도메인마다 다름. 메타 ADR이 지나치게 구체화

### 결정 6. 백엔드/프론트엔드 분리

#### 옵션 A. 메타 ADR이 BE/FE를 별도 산출물로 분리
- 장점: 두 자리가 다른 기술 결정(서버 vs 브라우저)을 가지므로 분리는 자연스럽다. 미래에 한쪽만 다른 언어로 바꾸기 쉬움
- 단점: 모노레포에서 두 자리를 어떻게 묶을지(workspace, multi-module 등)는 언어별

#### 옵션 B. 한 자리에 두 산출물 섞음
- 장점: 단일 디렉토리
- 단점: 빌드, 배포, 의존성이 섞여 유지보수가 어려움

### 결정 7. 인터페이스 설계와 디자인 패턴 준수

#### 옵션 A. 메타 ADR이 표준 디자인 패턴을 박음
- 장점: 같은 패턴(Repository, Service, Factory, DI)이 모든 언어에서 일관되게 적용됨. 한 언어 코드를 읽은 사람이 다른 언어 코드를 쉽게 읽음
- 단점: 패턴이 언어별로 다르게 표현됨(Java는 클래스, Node는 함수, Python은 둘 다)

#### 옵션 B. 언어별로 자체 패턴 결정
- 장점: 언어 관용 활용
- 단점: 일관성 깨짐. 6개월 뒤 다른 사람이 두 결을 새로 배워야 함

## 결정

7개 결정 모두 옵션 A를 채택한다. 즉 메타 ADR이 7원칙을 보편 원칙으로 박고, 언어별 ADR이 그 원칙을 자기 언어로 풀어낸다.

각 원칙의 표준은 다음과 같다.

### 결정 1: 보안 최고 우선순위

생성 코드의 모든 결정에서 보안이 첫 자리에 온다. 다음 항목이 모든 언어 ADR의 표준이다.

- **입력 검증**: 모든 외부 입력(HTTP 요청, 파일, 환경 변수)은 명시적 스키마로 검증한 뒤 도메인에 들어간다
- **시크릿 관리**: API 키, 비밀번호, 토큰은 환경 변수 또는 별도 시크릿 저장소에서 읽는다. 코드에 하드코딩 금지. .env는 git에 올리지 않음
- **인증/권한**: 공개 엔드포인트와 보호 엔드포인트가 명시적으로 구분되고, 보호 엔드포인트는 기본 차단(allow-list 방식)
- **SQL injection / XSS 방어**: 파라미터화된 쿼리, 출력 escape. raw SQL 문자열 조립 금지
- **HTTPS/TLS**: 운영 환경은 HTTPS 강제. HTTP는 redirect 또는 거부
- **보안 헤더**: 표준 HTTP 보안 헤더(CSP, HSTS, X-Frame-Options 등) 기본 적용
- **로그에 민감정보 금지**: 비밀번호, 토큰, 개인정보는 로그에서 마스킹 또는 제외

각 언어 ADR은 이 항목들이 자기 언어/프레임워크에서 어떤 라이브러리와 패턴으로 보장되는지 명시한다.

### 결정 2: MSA 준비를 위한 feature 단위 모듈 분리

모든 언어 ADR은 feature 단위(블럭 단위와 1:1)로 코드를 모듈로 나눈다. 각 feature 모듈은 다음을 담는다.

- 도메인(엔티티, 값 객체, 도메인 서비스)
- 응용 서비스(use case)
- 인프라(저장소 구현, 외부 API 클라이언트)
- 웹/표현(컨트롤러, 라우터, 스키마)

같은 feature의 자리는 같은 모듈 안에 모인다. feature 간 의존성은 명시적이고 단방향(결정 4 참조).

이 구조의 가치는 미래 MSA 분리 시 한 feature가 한 마이크로서비스로 자연스럽게 빠진다는 점. 같은 폴더가 같은 서비스가 된다.

### 결정 3: 언어별 표준 컨벤션 따름

각 언어 ADR은 그 언어 커뮤니티의 표준 컨벤션을 그대로 따른다.

- Node: Prettier + ESLint(Airbnb 또는 Standard 또는 Byeorim 자체) + 기본 Node/JS 관용
- Java: Google Java Style 또는 Spring Boot 컨벤션
- Python: PEP 8 + Black + isort

언어 간 비교(naming case 등)에서 작은 차이는 받아들인다. 각 언어 안에서의 일관성이 더 중요.

벼림 자체 컨벤션 표는 만들지 않는다. 언어 커뮤니티의 표준이 우리 표준.

### 결정 4: 단방향 의존성 그래프

생성 코드의 모듈 간 의존성은 단방향이고 검증 가능해야 한다. CLAUDE.md 섹션 3이 벼림 자체 코드(core ← catalog ← cli)에 박은 정신을 생성 코드에도 적용.

표준 의존성 방향:

```
domain     ← application ← infrastructure ← web
                                              ↑
                                          외부 입력
```

각 화살표가 "왼쪽이 오른쪽을 모른다"는 의미. domain은 application을 모르고, application은 infrastructure를 모르고, infrastructure는 web을 모른다. 외부 입력(HTTP 요청 등)은 web에서 받아 domain까지 단방향으로 흐른다.

각 언어 ADR은 이 방향을 강제하는 도구를 정한다(Java archunit, Node eslint-plugin-import, Python import-linter 등).

### 결정 5: 유지보수 우선 — 영리한 코드보다 읽기 쉬운 코드

가독성이 최우선이다. 다음이 모든 언어 ADR의 공통 표준이다.

- 함수는 한 가지 일만 한다. 짧을수록 좋다(언어별 권장 줄 수는 ADR마다)
- 변수와 함수 이름은 자기 설명적. `data`, `tmp` 같은 이름 회피
- 주석은 WHY를 다룬다. WHAT은 코드 이름이 다룸
- 영리한 한 줄보다 평범한 다섯 줄이 낫다
- 추상화는 세 번째 사례부터. 두 번까지는 중복 허용

정량 지표(함수 길이, 복잡도 한도)는 메타 ADR에서 정하지 않는다. 각 언어 ADR이 그 언어/도구에 맞게 정한다.

### 결정 6: 백엔드/프론트엔드 분리

생성 코드는 backend/와 frontend/ 두 자리로 분리된다. 둘은 다른 산출물이고 다른 빌드 도구를 가질 수 있다.

```
generated/
├── backend/
│   └── ... (언어별 백엔드 구조)
└── frontend/
    └── ... (언어별 프론트엔드 구조 — 이번 출시는 backend 우선)
```

이번 출시(MVP)는 backend 우선. frontend 자동 생성은 별도 ADR로 미룬다(사용자가 직접 짜거나 다음 출시 자리).

각 언어 ADR은 backend/ 안의 구조를 결정한다.

### 결정 7: 표준 디자인 패턴 + 명시적 인터페이스

다음 패턴이 모든 언어 ADR의 표준이다.

- **Repository 패턴**: 데이터 접근은 repository 인터페이스 뒤로 숨김. 도메인이 DB를 모름
- **Service 레이어**: 응용 로직(여러 도메인 객체를 엮는 use case)은 service에 둠
- **의존성 주입**: 컴포넌트 간 의존성은 명시적으로 주입(생성자 주입 또는 팩토리)
- **인터페이스 우선**: 모듈 경계에서 인터페이스로 약속을 박음. 구현 변경이 다른 모듈에 새지 않음
- **스키마 검증**: 입력/출력 경계에서 스키마로 검증(언어별 도구 다름)

각 언어 ADR은 이 패턴들이 자기 언어로 어떻게 표현되는지 명시한다(Java 클래스 vs Node 함수 vs Python 클래스+함수 등).

## 결과

### 긍정적
- 7원칙이 한 자리에 박혔다. 모든 언어 ADR이 같은 출발점에서 시작
- 미래에 새 언어(Go, Rust 등)가 들어올 때도 이 원칙을 받침대로 ADR을 짠다
- 사용자가 만든 산출물이 6개월 뒤 다음 사람이 이어받을 때 7원칙이 이미 박혀 있어 학습 비용이 작음
- 보안 최우선이 형식에 박혀서 잘못된 자동 생성으로 사용자가 위험에 노출되는 일이 적음
- feature 단위 모듈이 미래 MSA 분리를 자연스럽게 만든다. 한 폴더가 한 서비스로 빠짐

### 부정적 / 트레이드오프
- 메타 ADR이 추상적이라 각 원칙의 구체적 강도가 언어별 ADR에 의존. 한 언어 ADR이 약하면 그 언어 생성 코드의 품질이 약해짐
- 7원칙이 다 갖춰지려면 각 언어별 ADR이 8개 결정을 다뤄야 함. 언어별 ADR이 길어짐
- 보안 최우선이 가끔은 다른 자리(성능, 단순성)와 충돌. 그 자리 결정은 언어별 ADR로 미뤘으니 트레이드오프가 ADR마다 다를 수 있음
- BE/FE 분리에서 frontend 자동 생성은 미래 자리. 사용자는 그동안 frontend를 직접 짜야 함

### 미래 묶임
- 7원칙은 표준이다. 변경하려면 메타 ADR을 갱신하는 새 ADR이 필요(원칙 추가/제거/이름 변경)
- 각 언어 ADR(0018 Node, 0019 Java, 0020 Python)은 이 7원칙을 모두 다뤄야 한다. 빠뜨리면 그 언어 ADR이 이 ADR을 위반하는 자리
- 새 언어 ADR(예: Go, Rust)이 들어올 때도 이 7원칙을 그대로 따른다
- frontend 자동 생성, 정량 지표(함수 길이 등), feature 간 통신 패턴(REST/RPC/메시지 큐 등)은 별도 ADR
