# ADR 0037. Temper 인터랙티브 검토 흐름

- 상태: 채택
- 날짜: 2026-05-06
- 결정자: DevSmith
- 관계: ADR 0014(temper 책임과 test-scenarios.yml 형식)와 ADR 0036(fillTestCode 어댑터 인터페이스)은 그대로. ADR 0011의 인터랙티브 의존성 주입 패턴 확장. ADR 0029(smelt 검토), ADR 0032(shape 검토), ADR 0034(forge 검토)의 결을 temper에 옮기는 자리

## 맥락

smelt, shape, forge가 세 출시(ADR 0029/0032/0034)로 검토 자리를 받았다. AI 추천 또는 변환 결과를 보여주고 사용자가 한 번 보고 "이대로 가실래요?"를 묻는 결. temper는 그 자리가 비어있다.

temper는 forge처럼 비인터랙티브 변환 단계라 사용자 선택 자리가 없다. 다만 산출물(test-scenarios.yml)은 여전히 사용자에게 의미가 있다. contracts.yml의 endpoint마다 happy_path 시나리오가 한 개 만들어지고(ADR 0014 결정 3), AI 어댑터가 있으면 각 시나리오의 test_code가 채워진다(ADR 0036). 사용자는 그 결과를 보지 못한 채 다음 단계(set)로 넘어간다. 비기술 창업자(1순위 사용자) 시점에서 두 자리가 비어있다.

첫째, "어떤 시나리오가 만들어졌나" 자리가 안 보인다. CLI 출력이 "블럭 N개, 시나리오 M개" 한 줄이라 사용자가 test-scenarios.yml을 직접 열어 봐야 한다. 비기술 창업자에게 YAML을 들이미는 결(절대 금지선 5번)에 가깝다.

둘째, "test_code가 자기 스택에 맞는가" 자리가 비어있다. AI 어댑터가 채운 코드가 잘못 추론됐어도 사용자는 다음 단계로 넘어간 뒤에야 발견한다. 동행 톤(ADR 0003 결정 2) 정신상 한 번 멈춰 보여주는 자리가 비어있다.

이 두 자리를 한 결로 묶어 벼린다. forge의 ADR 0034와 같은 결로 인터랙티브 검토 흐름을 temper에도 박는다. temper도 사용자 선택 자리가 없으므로 ask는 변환을 돌리는 자리가 되고 confirm은 결과를 보여주는 자리가 된다.

## 검토한 옵션

### 결정 1. 검토 시점

#### 옵션 A. temper 변환 한 번 끝까지 돌린 뒤(시나리오 + test_code 채움) 보여주고 진행/다시
- 장점: 한 번 멈춤 자리. 사용자가 모든 결과를 한 자리에서 본다. forge의 ADR 0034 결정 1과 같은 결
- 단점: test_code 채움이 LLM 호출이라 시간이 걸림. 사용자가 결과 보기 전 대기 시간

#### 옵션 B. 시나리오 만든 뒤 보여주고 → test_code 채움 → 진행/다시
- 장점: 시나리오 결과를 먼저 빠르게 본다
- 단점: 멈춤 자리 두 개. 흐름이 길어짐. 비기술 창업자에게 부담

#### 옵션 C. 시나리오 + test_code 각각 두 단계로 confirm
- 장점: 미세 조정 가능
- 단점: 사용자가 한 단계에서 두 번 결정해야 함. 흐름이 길어짐

### 결정 2. 결과 표시 깊이

#### 옵션 A. 블럭별 한 줄 + endpoint별 메서드/path/시나리오 종류 줄
- 장점: 비기술 창업자가 "주문 생성 happy_path, 주문 목록 happy_path"처럼 한 자리에서 본다. 정보 충분, 부담 없음. 한 화면(블럭 5~10개)에 들어옴. forge의 ADR 0034 결정 2와 결이 일관
- 단점: test_code 자체는 안 보임. 코드 검토는 외부 검토 프롬프트(별도 ADR로 후속)로 미룸

#### 옵션 B. block_id와 시나리오 개수만
- 장점: 가장 간결
- 단점: 어떤 시나리오가 만들어졌는지 안 보임. 검토 의미 약함

#### 옵션 C. 각 시나리오의 test_code도 풀어 보여주기
- 장점: 코드까지 한 자리에서 검토
- 단점: 정보 과다. 한 블럭당 5개 endpoint × 시나리오 1개 × 코드 N줄이라 비기술 창업자가 막힘. 외부 검토 자리(별도 ADR)에서 다루는 게 결이 맞음

### 결정 3. "다시 만들게요"의 의미

#### 옵션 A. temper 변환 본체 다시(시나리오 같음 + test_code 채움 다시)
- 장점: forge/shape/smelt의 redo와 같은 결. claude 어댑터에서 LLM이 다른 코드를 줄 수 있어 의미 있음. mock에서는 결정적이라 같은 결과지만 흐름 일관
- 단점: mock 사용자에게는 redo가 헛흐름. 다만 안내 한 줄로 "어댑터가 결정적이라 같은 결과"를 풀 수 있음

#### 옵션 B. test_code 채움만 다시
- 장점: 시나리오 텍스트는 결정적이라 안 바뀌므로 LLM 호출만 다시
- 단점: 코드 자리 두 갈래(전체 vs test_code만). 흐름 복잡

#### 옵션 C. redo 없이 "확인" 한 갈래만
- 장점: 가장 단순
- 단점: forge/shape/smelt 결과 어긋남. 검토 의미가 약함

### 결정 4. adapter 미구현 시 동작

#### 옵션 A. test_code 채움 없이 진행, 인터랙티브 검토는 그대로
- 장점: temper가 LLM 없이도 동작(ADR 0036 결정 5 그대로). 인터랙티브 검토 자리는 살아남음. 모든 test_code가 TODO로 보이고 사용자가 그 자리를 인지. forge의 ADR 0034 결정 4와 짝
- 단점: 사용자가 test_code 채움을 기대했다가 못 받으면 미세하게 실망. 다만 "이번 흐름은 test_code 자동 채움 없이 진행됩니다" 안내로 풀어줌

#### 옵션 B. 에러로 중단
- 장점: 일관성
- 단점: temper는 ADR 0036부터 어댑터 옵셔널이었음. 후행 호환 깨짐

## 결정

### 결정 1: 변환 한 번 끝까지 돌린 뒤 검토 (옵션 A)

temper 본체를 한 번 끝까지(시나리오 + test_code 채움) 돌린 뒤 결과를 보여주고 진행/다시 select. forge의 ADR 0034 결정 1과 같은 결이라 사용자가 두 단계에서 같은 흐름을 따라간다.

### 결정 2: 블럭별 한 줄 + endpoint/시나리오 줄 (옵션 A)

검토 화면.

```
지금까지 만든 자리
  블럭 4개, 시나리오 11개
  (AI 어댑터: mock — test_code 11/11개 채워짐)

블럭별 자리
  주문 (resource, 5개 시나리오)
    POST   /orders             happy_path
    GET    /orders             happy_path
    GET    /orders/{id}        happy_path
    PUT    /orders/{id}        happy_path
    DELETE /orders/{id}        happy_path
  결제 (resource, 5개 시나리오)
    ...
  주문 검색 (query, 1개 시나리오)
    GET    /order-search       happy_path
  PG 연동 (internal — 시나리오 없음)
```

test_code 자체(코드 본문)는 이 자리에 안 보인다. 코드 검토는 외부 검토 프롬프트(후속 ADR)에서 다루는 게 결이 맞다. 비기술 창업자가 한 화면에서 "어떤 테스트 자리가 만들어졌나"를 본다.

시나리오 종류는 이번 출시 happy_path 한 가지. 미래에 에러/엣지가 들어오면 한 endpoint 줄에 여러 줄로 풀어 보여주는 자리가 자연스럽다(별도 ADR).

### 결정 3: "다시 만들게요"는 temper 본체 다시 (옵션 A)

검토 select.

```
이대로 가실래요?
❯ 예, 다음 단계로
  아니오, 다시 만들게요
```

"다시 만들게요"를 누르면 temper 본체를 다시 돌린다. mock 어댑터는 결정적이라 같은 결과를 만들지만 흐름은 일관(forge/shape/smelt와 같은 결). claude 어댑터는 LLM 응답이 달라질 수 있어 의미가 있다. 사용자 의지로 무한 루프 가능(차단 자리 없음, 동행 톤).

mock 어댑터에서 redo가 헛흐름임을 사용자에게 알리는 안내 한 줄을 추가한다.

```
어댑터가 결정적이라 다시 만들어도 같은 test_code가 채워질 거예요.
```

이 안내는 mock일 때만 보인다. claude 같은 비결정 어댑터에서는 안 보인다.

### 결정 4: adapter 미구현 시 test_code 없이 진행 (옵션 A)

`runTemper`의 옵셔널 adapter 결(ADR 0036)을 그대로 둔다. `interactiveTemper`도 adapter가 없거나 `fillTestCode`를 구현하지 않으면 test_code는 모두 `TODO`로 채우고 인터랙티브 검토는 그대로 진행한다. 검토 화면 헤더에 안내.

```
지금까지 만든 자리
  블럭 4개, 시나리오 11개
  (어댑터가 test_code 채움을 지원하지 않아 모두 TODO로 남아있어요)
```

기존 `runTemper`의 비대화 시그니처는 후행 호환을 위해 그대로 유지(ADR 0036 결정 5와 같은 결). `bin/beoreum.js`의 temper 핸들러만 `interactiveTemper`로 바꾼다.

## 결과

### 긍정적
- 비기술 창업자가 test-scenarios.yml을 직접 열지 않고도 어떤 시나리오가 만들어졌는지 한 화면에서 본다. 절대 금지선 5번(YAML을 사용자에게 들이밀지 않는다) 정신을 temper에서도 지킨다
- AI 어댑터가 채운 test_code가 마음에 안 들면 한 자리에서 다시 만들 수 있다. 다음 단계로 넘어간 뒤에야 발견하던 자리가 풀린다
- forge/shape/smelt의 인터랙티브 검토 결을 temper에 그대로 옮겨 사용자가 네 단계에서 같은 사용 패턴을 따라간다
- adapter 미구현 시 graceful degradation으로 temper가 깨지지 않음(ADR 0036의 결을 그대로 보존)
- `runTemper`의 시그니처가 안 바뀌어 후행 호환 유지. 비대화 호출이 필요한 자리(테스트, 자동화)에서 그대로 사용

### 부정적 / 트레이드오프
- claude 어댑터를 쓰는 사용자에게 매번 LLM 호출이 발생. test_code는 시나리오마다 한 번이라 forge보다 호출 수가 더 많음. 다만 redo 자리에서만 다시 호출. mock에서는 LLM 호출 없음
- mock 어댑터에서 "다시 만들게요"가 같은 결과를 만들어 헛흐름. 안내 한 줄로 풀지만 인지 비용은 있음
- test_code 자체(코드 본문)는 이 화면에 안 보임. 코드 검토는 외부 검토 프롬프트 후속 ADR(PR 3)에서 다루는 약속이 한 자리 더 비어있는 결로 보일 수 있음
- 검토 단계 한 번 추가됨. 흐름이 살짝 길어짐. 한 번 멈춤이라 부담 작음

### 미래 묶임
- `interactiveTemper` 시그니처와 의존성 주입 패턴(confirmScenarios)은 표준. 변경하려면 새 ADR
- 검토 화면의 표시 깊이(블럭별 한 줄 + endpoint/시나리오 줄)는 표준. test_code까지 풀어 보여주는 자리는 별도 ADR
- "예/다시 만들게요" 두 갈래는 표준. 부분 재생성(예: 한 시나리오만 다시)을 추가하려면 새 ADR
- mock 결정성 안내 문구의 자리는 표준. forge와 같은 결로 어댑터 인터페이스에 박힐 자리(미래 ADR)
- `runTemper`의 비대화 시그니처는 후행 호환 약속. 이 약속을 깨려면 새 ADR

## 링크

- 갱신 대상: ADR 0011 (인터랙티브 의존성 주입 패턴 확장)
- 입력 의존: ADR 0014 (temper 책임과 test-scenarios.yml 형식, 그대로 유지), ADR 0036 (fillTestCode와 옵셔널 adapter, 그대로 유지)
- 동행 톤: ADR 0003 결정 2
- 후속 작업 후보: 외부 검토 프롬프트(test-scenarios-review-prompt.md, test_code 자체 검토 자리) ADR(Temper PR 3 자리)
