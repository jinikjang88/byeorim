# ADR 0034. Forge 인터랙티브 검토 흐름

- 상태: 채택
- 날짜: 2026-05-05
- 결정자: DevSmith
- 관계: ADR 0013(forge 책임과 contracts.yml 형식)과 ADR 0023(extractSchema)은 그대로. ADR 0011의 인터랙티브 의존성 주입 패턴 확장. ADR 0029(smelt 검토)와 ADR 0032(shape 검토)의 결을 forge에 옮기는 자리

## 맥락

smelt와 shape가 두 출시(ADR 0029/0032)로 검토 자리를 받았다. AI 추천을 보여주고 사용자가 결과를 한 번 보고 "이대로 가실래요?"를 묻는 결. forge는 그 자리가 비어있다.

forge는 비인터랙티브 변환 단계라 사용자 선택 자리가 없다. 다만 산출물(contracts.yml)은 여전히 사용자에게 의미가 있다. block.api_style → endpoints 매핑(ADR 0013 결정 3)으로 한 블럭이 5개, 1개, 0개의 endpoint를 갖는다. AI 어댑터가 있으면 각 endpoint의 request_schema/response_schema를 채운다(ADR 0023). 사용자는 그 결과를 보지 못한 채 다음 단계(temper)로 넘어간다. 비기술 창업자(1순위 사용자) 시점에서 두 자리가 비어있다.

첫째, "어떤 endpoint가 만들어졌나" 자리가 안 보인다. CLI 출력이 "블럭 N개, 엔드포인트 M개" 한 줄이라 사용자가 contracts.yml을 직접 열어 봐야 한다. 비기술 창업자에게 YAML을 들이미는 결(절대 금지선 5번)에 가깝다.

둘째, "schema가 자기 도메인에 맞는가" 자리가 비어있다. AI 어댑터가 채운 schema가 잘못 추론됐어도 사용자는 다음 단계로 넘어간 뒤에야 발견한다. 동행 톤(ADR 0003 결정 2) 정신상 한 번 멈춰 보여주는 자리가 비어있다.

이 두 자리를 한 결로 묶어 벼린다. shape의 ADR 0032와 같은 결로 인터랙티브 검토 흐름을 forge에도 박는다. 다만 forge는 사용자 선택 자리가 없으므로 ask는 변환을 돌리는 자리가 되고 confirm은 결과를 보여주는 자리가 된다.

## 검토한 옵션

### 결정 1. 검토 시점

#### 옵션 A. forge 변환 한 번 끝까지 돌린 뒤(skeleton + schema 채움) 보여주고 진행/다시
- 장점: 한 번 멈춤 자리. 사용자가 모든 결과를 한 자리에서 본다. shape의 ADR 0032 결정 3과 같은 결
- 단점: schema 채움이 LLM 호출이라 시간이 걸림. 사용자가 결과 보기 전 대기 시간

#### 옵션 B. skeleton 만든 뒤 보여주고 → schema 채움 → 진행/다시
- 장점: skeleton 결과를 먼저 빠르게 본다
- 단점: 멈춤 자리 두 개. 흐름이 길어짐. 비기술 창업자에게 부담

#### 옵션 C. skeleton + schema 각각 두 단계로 confirm
- 장점: 미세 조정 가능
- 단점: 사용자가 한 단계에서 두 번 결정해야 함. 흐름이 길어짐

### 결정 2. 결과 표시 깊이

#### 옵션 A. 블럭별 한 줄 + 메서드/path 줄(한 화면 요약)
- 장점: 비기술 창업자가 "주문 만들기, 주문 목록 보기"처럼 한 자리에서 본다. 정보 충분, 부담 없음. 한 화면(블럭 5~10개)에 들어옴
- 단점: schema 자체는 안 보임. schema 검토는 외부 검토 프롬프트(별도 ADR로 후속)로 미룸

#### 옵션 B. block_id와 endpoint 개수만
- 장점: 가장 간결
- 단점: 어떤 endpoint가 만들어졌는지 안 보임. 검토 의미 약함

#### 옵션 C. 각 endpoint의 request/response schema도 풀어 보여주기
- 장점: schema까지 한 자리에서 검토
- 단점: 정보 과다. 한 블럭당 5개 endpoint × 2 schema라 비기술 창업자가 막힘. 외부 검토 자리(별도 ADR)에서 다루는 게 결이 맞음

### 결정 3. "다시 만들게요"의 의미

#### 옵션 A. forge 변환 본체 다시(skeleton 같음 + schema 채움 다시)
- 장점: shape/smelt의 redo와 같은 결. claude 어댑터에서 LLM이 다른 schema를 줄 수 있어 의미 있음. mock에서는 결정적이라 같은 결과지만 흐름 일관
- 단점: mock 사용자에게는 redo가 헛흐름. 다만 안내 한 줄로 "어댑터가 결정적이라 같은 결과"를 풀 수 있음

#### 옵션 B. schema 채움만 다시
- 장점: skeleton은 결정적이라 안 바뀌므로 LLM 호출만 다시
- 단점: 코드 자리 두 갈래(전체 vs schema만). 흐름 복잡

#### 옵션 C. redo 없이 "확인" 한 갈래만
- 장점: 가장 단순
- 단점: shape/smelt의 결과 어긋남. 검토 의미가 약함

### 결정 4. adapter 미구현 시 동작

#### 옵션 A. schema 채움 없이 진행, 인터랙티브 검토는 그대로
- 장점: forge가 LLM 없이도 동작(ADR 0023 결정 3 그대로). 인터랙티브 검토 자리는 살아남음. 모든 schema가 TODO로 보이고 사용자가 그 자리를 인지. shape의 ADR 0032 결정 4와 짝
- 단점: 사용자가 schema 채움을 기대했다가 못 받으면 미세하게 실망. 다만 "이번 흐름은 schema 자동 채움 없이 진행됩니다" 안내로 풀어줌

#### 옵션 B. 에러로 중단
- 장점: 일관성
- 단점: forge는 ADR 0023부터 어댑터 옵셔널이었음. 후행 호환 깨짐

## 결정

### 결정 1: 변환 한 번 끝까지 돌린 뒤 검토 (옵션 A)

forge 본체를 한 번 끝까지(skeleton + schema 채움) 돌린 뒤 결과를 보여주고 진행/다시 select. shape의 ADR 0032 결정 3과 같은 결이라 사용자가 두 단계에서 같은 흐름을 따라간다.

### 결정 2: 블럭별 한 줄 + 메서드/path 줄 (옵션 A)

검토 화면.

```
지금까지 만든 자리
  블럭 4개, 엔드포인트 11개
  (AI 어댑터: mock — schema 22개 채워짐)

블럭별 자리
  주문 (resource, 5개 endpoint)
    POST   /orders             주문 생성
    GET    /orders             주문 목록 조회
    GET    /orders/{id}        주문 한 건 조회
    PUT    /orders/{id}        주문 수정
    DELETE /orders/{id}        주문 삭제
  결제 (resource, 5개 endpoint)
    ...
  주문 검색 (query, 1개 endpoint)
    GET    /order-search       주문 검색
  PG 연동 (internal — 공개 API 없음)
```

schema 자체(필드명, 타입)는 이 자리에 안 보인다. schema 검토는 외부 검토 프롬프트(후속 ADR)에서 다루는 게 결이 맞다. 비기술 창업자가 한 화면에서 "어떤 일이 일어날 자리가 만들어졌나"를 본다.

### 결정 3: "다시 만들게요"는 forge 본체 다시 (옵션 A)

검토 select.

```
이대로 가실래요?
❯ 예, 다음 단계로
  아니오, 다시 만들게요
```

"다시 만들게요"를 누르면 forge 본체를 다시 돌린다. mock 어댑터는 결정적이라 같은 결과를 만들지만 흐름은 일관(shape/smelt와 같은 결). claude 어댑터는 LLM 응답이 달라질 수 있어 의미가 있다. 사용자 의지로 무한 루프 가능(차단 자리 없음, 동행 톤).

mock 어댑터에서 redo가 헛흐름임을 사용자에게 알리는 안내 한 줄을 추가한다.

```
어댑터가 결정적이라 같은 schema가 다시 채워질 거예요.
```

이 안내는 mock일 때만 보인다. claude 같은 비결정 어댑터에서는 안 보인다.

### 결정 4: adapter 미구현 시 schema 없이 진행 (옵션 A)

`runForge`의 옵셔널 adapter 결(ADR 0023)을 그대로 둔다. `interactiveForge`도 adapter가 없거나 `extractSchema`를 구현하지 않으면 schema는 모두 `TODO`로 채우고 인터랙티브 검토는 그대로 진행한다. 검토 화면 헤더에 안내.

```
지금까지 만든 자리
  블럭 4개, 엔드포인트 11개
  (어댑터가 schema 채움을 지원하지 않아 모두 TODO로 남아있어요)
```

기존 `runForge`의 비대화 시그니처는 후행 호환을 위해 그대로 유지(ADR 0023 결정 3과 같은 결). `bin/beoreum.js`의 forge 핸들러만 `interactiveForge`로 바꾼다.

## 결과

### 긍정적
- 비기술 창업자가 contracts.yml을 직접 열지 않고도 어떤 endpoint가 만들어졌는지 한 화면에서 본다. 절대 금지선 5번(YAML을 사용자에게 들이밀지 않는다) 정신을 forge에서도 지킨다
- AI 어댑터가 채운 schema가 마음에 안 들면 한 자리에서 다시 만들 수 있다. 다음 단계로 넘어간 뒤에야 발견하던 자리가 풀린다
- shape/smelt의 인터랙티브 검토 결을 forge에 그대로 옮겨 사용자가 세 단계에서 같은 사용 패턴을 따라간다
- adapter 미구현 시 graceful degradation으로 forge가 깨지지 않음(ADR 0023의 결을 그대로 보존)
- `runForge`의 시그니처가 안 바뀌어 후행 호환 유지. 비대화 호출이 필요한 자리(테스트, 자동화)에서 그대로 사용

### 부정적 / 트레이드오프
- claude 어댑터를 쓰는 사용자에게 매번 LLM 호출이 발생. 다만 forge는 변환 단계라 한 번이면 끝남. mock에서는 LLM 호출 없음
- mock 어댑터에서 "다시 만들게요"가 같은 결과를 만들어 헛흐름. 안내 한 줄로 풀지만 인지 비용은 있음
- schema 자체(필드명, 타입)는 이 화면에 안 보임. schema 검토는 외부 검토 프롬프트 후속 ADR에서 다루는 약속이 한 자리 더 비어있는 결로 보일 수 있음
- 검토 단계 한 번 추가됨. 흐름이 살짝 길어짐. 한 번 멈춤이라 부담 작음

### 미래 묶임
- `interactiveForge` 시그니처와 의존성 주입 패턴(ask/confirm)은 표준. 변경하려면 새 ADR
- 검토 화면의 표시 깊이(블럭별 한 줄 + 메서드/path 줄)는 표준. schema까지 풀어 보여주는 자리는 별도 ADR
- "예/다시 만들게요" 두 갈래는 표준. 부분 재생성(예: 한 블럭만 다시)을 추가하려면 새 ADR
- mock 결정성 안내 문구의 자리는 표준. 다른 어댑터가 결정성을 알리는 결은 어댑터 인터페이스에 박힐 자리(미래 ADR)
- `runForge`의 비대화 시그니처는 후행 호환 약속. 이 약속을 깨려면 새 ADR

## 링크
- 결의 짝: ADR 0029 (smelt 검토 흐름), ADR 0032 (shape 검토 흐름, 같은 결을 forge에 옮김)
- 갱신 대상: ADR 0011 (인터랙티브 의존성 주입 패턴 확장)
- 입력 의존: ADR 0013 (forge 책임과 contracts.yml 형식, 그대로 유지), ADR 0023 (extractSchema와 옵셔널 adapter, 그대로 유지)
- 동행 톤: ADR 0003 결정 2
- 후속 작업 후보: 외부 검토 프롬프트(contracts-review-prompt.md, schema 자체 검토 자리) ADR
- 관련 정책: CLAUDE.md 섹션 0(1순위 사용자), 섹션 8(파일당 책임), 섹션 10(글쓰기 원칙)
