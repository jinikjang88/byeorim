# ADR 0002. 6단계 메타포와 작업 어휘 결정

- 상태: 채택
- 날짜: 2026-04-27
- 결정자: DevSmith

## 맥락

ADR 0001에서 프로젝트 이름을 Byeorim으로 결정한 직후, 두 가지 후속 결정이 따라왔다.

첫째, 기존 5단계(Smelt, Shape, Forge, Temper, Inspect)가 충분한가. 작업하던 중 meta-smelt라는 이름의 기능이 별도로 있었다. 사용자의 자연어 입력에서 도메인 블럭 카탈로그 자체를 자동 생성하는 기능이다. 이게 5단계 어디에도 들어맞지 않았다. Smelt 이전에 일어나는 일이지만, 별칭이나 보조 기능이 아니라 그 자체로 독립된 단계의 무게를 가지고 있었다. 게다가 이 단계에서 Reality Check(시장 직시 리포트)를 함께 출력하면 벼림의 1순위 사용자(비기술 창업자)에게 가장 중요한 가치가 만들어진다. 즉 단계로 승격시킬 이유가 충분했다.

둘째, 이름은 한국어로 가기로 했는데 작업 어휘(CLI 명령어, 함수명)도 한국어로 갈 것인가. 5단계를 모두 한국어로 표기하는 안(jeryeon, bitda, danjo, dadeum, geomsu 등)을 검토했다. 결과는 부정적이었다. 한국어 영문표기는 변형이 흩어진다. jeryeon은 jeryun, jelyeon, jeoryeon 등 6가지 변형으로 흩어지고, damgeum은 damgum이 더 자주 쳐진다. 매일 사용하는 CLI 명령어로는 부적합했다.

추가로 명령어 작명 시 npm/GitHub 점유 충돌도 고려해야 했다. 다행히 서브커맨드(byeorim prospect)는 독립 패키지가 아니어서 충돌 무관임을 확인했다.

## 검토한 옵션

이 ADR은 세 가지 묶인 결정을 다룬다. 각 결정마다 옵션을 정리한다.

### 결정 1. 단계 수

#### 옵션 A. 5단계 유지 (Smelt~Inspect)
- 장점: 기존 메타포 그대로 유지. 변경 부담 없음
- 단점: meta-smelt 기능이 단계 어디에도 들어맞지 않음. Reality Check를 어디 둘지 애매해짐

#### 옵션 B. 6단계로 확장 (Prospect 추가)
- 장점: meta-smelt를 0번 단계로 승격해 메타포에 자연스럽게 편입. Reality Check가 Prospect 안에 자리 잡음. "광맥 탐색"이라는 비유가 대장장이 메타포와 정확히 일치
- 단점: 단계 수 증가. 학습할 명령어 하나 더 추가. 기존 5단계 사용자가 적응 필요

#### 옵션 C. 7단계 이상으로 확장
- 장점: 더 세밀한 단계 분할 가능
- 단점: CLAUDE.md 사용자 우선순위 1번(비기술 창업자)에게 인지 부담 증가. 6단계도 사실 비개발자에게는 많은 편

### 결정 2. 작업 어휘 (CLI 명령어와 함수명)

#### 옵션 A. 영문 메타포 그대로 (smelt, shape, forge, temper, inspect)
- 장점: 영어권 즉시 통함. 표기 변형 없음. 짧고 명확
- 단점: 프로젝트 이름이 한국어인데 작업 어휘만 영문이라 결이 갈림

#### 옵션 B. 한국어 영문표기 (jeryeon, bitda, danjo, damgeum, geomsu)
- 장점: 정체성 일관성. 프로젝트 전체가 한국어 결로 통일
- 단점: 표기 변형 다발. jeryeon은 6가지 변형으로 흩어지고 damgeum은 damgum이 더 자주 쳐진다. CLI 사용성 저하

#### 옵션 C. 영문 메타포 + 한국어 한글 병기 (문서·UI에서)
- 장점: 두 결의 장점 일부씩 확보
- 단점: 두 결의 강점 일부씩 잃음. 어중간한 타협

### 결정 3. Reality Check의 위치

#### 옵션 A. Prospect 안에 포함
- 장점: 광맥 탐색이라는 메타포 안에 광맥의 가치 평가가 자연스럽게 들어감. 사용자 첫 단계에서 시장 직시
- 단점: Prospect 단계가 두 가지 일을 함(카탈로그 발견 + Reality Check)

#### 옵션 B. 별도 단계로 추가
- 장점: 각 단계의 단일 책임 명확
- 단점: 7단계가 됨. 인지 부담 추가

#### 옵션 C. Inspect 안에서 시장 관점으로 포함
- 장점: 출시 직전 마지막 점검과 함께 시장도 본다는 흐름
- 단점: 사용자가 코드를 다 만든 뒤 시장이 없다는 걸 깨닫는 일이 막히지 않는다. 너무 늦다

## 결정

세 결정을 다음과 같이 채택한다.

### 결정 1: 6단계로 확장 (옵션 B)

기존 5단계(Smelt, Shape, Forge, Temper, Inspect) 앞에 Prospect를 추가해 6단계로 만든다. Prospect는 사용자의 자연어에서 도메인 블럭 카탈로그를 자동 발견하고, Reality Check를 함께 출력한다.

6단계 한국어 이름과 영문 명령어, 3글자 별칭은 다음과 같다.

- 0번. 탐광 (prospect, prs): 광맥 탐색. 도메인 카탈로그 발견과 Reality Check
- 1번. 제련 (smelt, sml): 의도 추출, 블럭 선택, 의존성 해결
- 2번. 빚다 (shape, shp): 아키텍처 결정과 ADR 기록
- 3번. 단조 (forge, frg): 계약 우선 구현과 코드 생성
- 4번. 다듬 (temper, tmr): 자동 검증과 Given-When-Then 테스트
- 5번. 비춤 (inspect, ins): 다관점 리뷰

> 갱신 (2026-04-28, ADR 0006): 다듬과 비춤 사이에 세움(set, set)이 추가되어 7단계가 됐다. 세움은 계약과 테스트 의도로부터 실제 코드를 생성하고 컴파일·테스트로 자립을 확인한다. 본 ADR의 6단계 결정은 그 시점의 결정이고, 현행 표준은 ADR 0006이다.

### 결정 2: 영문 메타포 표준, 한국어 한글은 문서·UI 병기 (옵션 A 기반)

CLI 명령어, 함수명, 코드 어휘는 영문 메타포(prospect, smelt, shape, forge, temper, inspect)를 표준으로 한다. 한국어 영문표기(jeryeon 등)는 별칭으로도 지원하지 않는다.

문서, MANIFESTO, 사용자 응답, 시각형 모드 UI에서는 한국어 한글을 병기한다(예: "탐광(Prospect)"). 6단계의 본질을 한국어로 이해하되, 손가락으로 치는 명령어는 영문으로 친다.

3글자 별칭(prs, sml, shp, frg, tmr, ins)은 빠른 입력을 위해 함께 지원한다.

### 결정 3: Reality Check는 Prospect 안에 포함 (옵션 A)

Reality Check 리포트는 Prospect 단계의 두 번째 산출물이다. 첫 번째는 catalog/ 디렉토리(블럭 카탈로그), 두 번째는 reality-check.md(시장 직시 리포트)이다. Prospect 단계를 광맥 탐색에 비유하면, catalog는 *광맥의 구조*이고 reality-check는 *광맥의 가치*이다.

Reality Check 6영역(시장 포화, 진입 비용, 양면 시장, 법적 리스크, 수익 모델, 묘지)의 상세 정의는 별도 ADR로 다룬다.

## 결과

### 긍정적
- 메타포 일관성: 6단계 모두 대장장이 메타포 안에서 자연스럽게 흐른다
- 정체성 일관성: 프로젝트 이름은 한국어, 작업 어휘는 영문이라는 분명한 정책이 잡혔다
- 사용자 경험: 표기 변형 문제 없이 매일 쓰는 명령어가 단단해졌다
- 차별화: Prospect와 Reality Check의 결합은 다른 SDD 도구에 없는 자리를 차지한다
- 학습성: 한 단계가 한 영문 동사이고 그 옆에 한국어 한글이 함께 보인다. 두 언어로 이해할 수 있다

### 부정적 / 트레이드오프
- 단계 수 증가: 5단계에서 6단계로 늘어 학습 부담이 살짝 증가했다
- Prospect 단계의 책임이 둘이다(카탈로그 발견 + Reality Check). 단일 책임 원칙 관점에서는 약간 흠집이다. 다만 두 산출물이 같은 입력(사용자 자연어)에서 같이 나오므로 분리할 실익이 적다
- 한국어 영문표기를 명령어로 채택하지 못한 아쉬움. 정체성 측면에서는 한국어 명령어가 더 강할 수 있었다. 그러나 표기 변형 문제가 사용성을 해친다는 검증 결과를 따랐다
- 영문 명령어를 표준으로 두면서 한국어 한글 병기는 별도 노력으로 유지해야 한다. 문서 일관성 관리 부담이 있다

### 미래 묶임
- 6단계 명령어 이름(prospect, smelt, shape, forge, temper, inspect)은 표준이다. 다른 단어로 변경하려면 별도 ADR로 결정한다
- 별칭은 3글자 영문 단축형(prs, sml, shp, frg, tmr, ins)으로 고정한다. 다른 길이나 다른 글자 조합은 채택하지 않는다
- 한국어 영문표기 명령어(jeryeon, bitda 등)는 향후에도 지원하지 않는다. 도입하려면 ADR로 결정한다
- 새 단계를 추가하거나 기존 단계를 분할하려면 별도 ADR로 결정한다 (이 조항이 ADR 0006으로 처음 호출됐다)
