# ADR 0006. 코드 출력과 검증을 위한 세움(Set) 단계 추가

- 상태: 채택
- 날짜: 2026-04-28
- 결정자: DevSmith

## 맥락

ADR 0002가 6단계 메타포(탐광·제련·빚다·단조·다듬·비춤)를 표준으로 박았다. 같은 ADR의 미래 묶임 절은 새 단계 추가나 기존 단계 분할은 별도 ADR로 결정하라고 명시했다. 이번 결정이 그 조항이 처음으로 호출되는 자리다.

forge-protocol v0.5.0은 inspect 외에도 emit과 verify 두 단계를 따로 가지고 있었다. emit은 contracts.yml과 architecture.yml을 입력으로 실제 Spring Boot 컨트롤러, DTO, 빌드 파일, JUnit 테스트 클래스를 `.forge/generated/backend/`에 출력한다. verify는 그 결과물이 컴파일되는지, 다듬 단계에서 정의한 테스트가 실제로 통과하는지 확인하고 결과 리포트를 남긴다. 두 단계는 분리되어 있지만 짝이다. emit 없는 verify는 검증할 대상이 없고, verify 없는 emit은 약속을 지키는지 모른다.

벼름의 6단계는 다듬에서 끝나기 직전 비춤으로 넘어간다. 그런데 다듬의 정의는 "Given-When-Then으로 의도를 적고, 속성 기반 검증으로 조합을 본다. 통과하지 못한 코드는 다음 단계로 못 간다"였다. 여기서 모순이 드러난다. 다듬에 "통과하지 못한 코드"가 등장하려면 코드 자체가 이미 존재해야 한다. 그러나 단조까지의 결과물은 계약(contracts.yml)이지 코드가 아니다. 즉 6단계는 코드를 누가 언제 만드는지에 대한 답을 가지고 있지 않았다. emit이 들어갈 자리가 없었던 셈이다.

비춤의 정의는 "보안, 성능, 운영, 확장성, 그리고 다시 시장의 관점까지. 여러 각도에서 한 번 더 본다"이다. 코드를 생성하고 컴파일을 통과시키는 일은 비춤의 다관점 검수와 결이 다르다. 흡수시키면 비춤이 두 일을 함께 지게 되고, 단일 책임 원칙 관점에서 흠이 생긴다. ADR 0002가 Prospect의 두 책임(카탈로그 발견 + Reality Check)을 묶을 때는 두 산출물이 같은 입력에서 같이 나온다는 명분이 있었다. 비춤에 emit과 verify를 추가하는 일은 그 명분이 없다. 입력이 다르고 산출물이 다르고 사용자에게 보이는 결도 다르다.

따라서 새 단계가 필요하다. 그 단계의 이름과 위치를 결정한다.

## 검토한 옵션

### 결정 1. 비춤이 emit과 verify를 흡수할지, 별도 단계로 둘지

#### 옵션 A. 비춤이 흡수
- 장점: 단계 수가 6으로 유지된다. 학습 부담이 늘지 않는다
- 단점: 비춤이 "여러 각도에서 한 번 더 본다"는 정의에서 멀어진다. 코드 생성과 다관점 검수는 입력도 산출물도 다르다. 흡수 시 비춤이 두 일을 지게 된다

#### 옵션 B. 별도 단계 한 개로 묶음
- 장점: 단일 책임이 명확해진다. emit과 verify는 짝이라 같은 단계 안에서 자연스럽다. 비춤은 다관점 검수에 집중한다
- 단점: 단계 수가 7로 늘어난다. 비기술 창업자 인지 부담이 살짝 증가한다

#### 옵션 C. 별도 단계 두 개(emit과 verify를 분리)
- 장점: 각 단계의 단일 책임이 가장 강하다
- 단점: 단계 수가 8로 늘어난다. CLAUDE.md 사용자 우선순위 1번에게 부담이 커진다. emit 없는 verify는 의미가 없으므로 분리 실익이 적다

### 결정 2. 새 단계 이름

#### 옵션 A. 갈음(Hone)
- 장점: 대장장이 메타포에 가장 충실하다. 열처리 뒤 날을 가는 동작이 정확히 이 자리다
- 단점: 다듬(Temper)이 이미 "다듬는다"는 의미라 갈음과 거의 겹친다. 두 단계가 사용자에게 같은 일처럼 들릴 위험이 있다

#### 옵션 B. 마감(Finish)
- 장점: 일상어라 비기술 창업자에게 의미가 빠르게 전달된다. 단조와 다듬 뒤 마무리 손질이라는 흐름이 자연스럽다
- 단점: 그 뒤에 비춤이 한 번 더 있다. 마감이라는 어감은 끝맺음을 강하게 암시해서 이어지는 비춤이 군더더기처럼 느껴진다

#### 옵션 C. 세움(Set)
- 장점: 도구를 일으켜 세운다는 의미가 코드 emission(코드를 짓는 일)과 verify(자기 발로 서는지 확인하는 일) 두 동작을 한 단어로 잡는다. 다듬과 의미가 겹치지 않는다. 마감처럼 끝맺음 어감이 없어 비춤이 자연스럽게 따라온다. 영문 set은 짧고 손가락에 익숙한 동사다
- 단점: 갈음에 비해 대장장이 메타포의 정확도는 살짝 떨어진다. 다만 벼름의 6단계는 처음부터 메타포 충실도와 의미 분리 사이의 균형을 잡아왔다(빚다, 단조의 한국어 결도 영문과 1:1이 아니다)

### 결정 3. 새 단계 위치

#### 옵션 A. 다듬과 비춤 사이
- 장점: 다듬에서 정의한 테스트 의도가 새 단계에서 실제 코드 위로 돌아간 뒤, 비춤이 그 결과물을 다관점으로 점검한다. 흐름이 직선적이다
- 단점: 없음. 다른 위치는 의미가 통하지 않는다(비춤 뒤에 코드 생성을 두면 점검 대상이 사라진다)

#### 옵션 B. 비춤 뒤
- 장점: 비춤이 "출시 준비 점검"으로만 남고, 코드 출력이 마지막에 온다
- 단점: 비춤이 검수할 대상이 사라진다. 흐름이 부서진다

## 결정

### 결정 1: 별도 단계 한 개로 묶는다 (옵션 B)

비춤은 다관점 검수에 집중한다. emit과 verify는 짝으로 한 새 단계에 들어간다.

### 결정 2: 이름은 세움(Set)으로 간다 (옵션 C)

한국어 세움, 영문 명령어 set, 별칭도 set 그대로 쓴다(3글자). 별칭이 본명과 같아 학습 비용이 가장 낮은 자리다.

갈음(Hone)을 택하지 않은 결정적 이유는 다듬과의 의미 중복이다. 다듬의 정의가 "다듬는다"이므로 갈음(간다)과 한국어 어감이 거의 같다. 두 단계가 사용자에게 한 일로 들리면 7단계로 확장한 보람이 사라진다.

마감(Finish)을 택하지 않은 결정적 이유는 그 뒤에 비춤이 한 번 더 있다는 사실이다. 마감이라는 끝맺음 어감 뒤에 비춤이 따라오면 어느 한쪽이 군더더기로 보인다.

세움은 코드를 짓고(emit) 그 코드가 자기 발로 서는지 확인하는 일(verify)을 한 단어로 잡는다. 도구가 비로소 세상에 일어서는 자리다.

### 결정 3: 위치는 다듬과 비춤 사이 (옵션 A)

7단계 순서는 다음과 같다.

- 0번. 탐광 (prospect, prs): 광맥 탐색
- 1번. 제련 (smelt, sml): 의도 추출과 블럭 선택
- 2번. 빚다 (shape, shp): 아키텍처 결정과 ADR 기록
- 3번. 단조 (forge, frg): 계약 우선 정의
- 4번. 다듬 (temper, tmr): Given-When-Then 테스트 의도와 속성 기반 검증
- 5번. **세움 (set, set)**: 계약과 테스트 의도에서 실제 코드 생성, 컴파일과 테스트 실행으로 자립 확인
- 6번. 비춤 (inspect, ins): 보안, 성능, 운영, 확장성, 시장 다관점 검수

세움이 들어오면서 다듬의 정의도 명확해진다. 다듬은 테스트 의도를 정의하는 자리이고, 세움이 그 의도를 실제 코드 위에서 돌린다. 다듬에 적힌 "통과하지 못한 코드는 다음 단계로 못 간다"는 약속의 실체는 세움 단계가 진다. 다듬은 "통과해야 할 의도"를 빚고, 세움이 통과 여부를 본다.

## 결과

### 긍정적
- 비춤이 다관점 검수라는 본 책임에 머문다. emit과 verify가 그 책임을 흐리지 않는다
- 다듬과 세움의 분업이 명확하다. 다듬은 무엇이 통과해야 하는지, 세움은 실제로 통과하는지를 본다
- 영문 명령어 set은 본명과 별칭이 같아 학습 비용이 0에 가깝다
- 7단계 메타포가 forge-protocol v0.5.0의 6단계(prospect 누락 상태)를 그대로 흡수한다. 이전 코드의 실측 단계를 잃지 않는다

### 부정적 / 트레이드오프
- 단계 수가 6에서 7로 늘었다. CLAUDE.md 사용자 우선순위 1번 비기술 창업자에게 인지 부담이 살짝 추가된다. 다만 세움은 자동 실행에 가깝고(코드 생성과 테스트 실행) 직접 의사결정이 적은 자리라 학습 비용이 다른 단계보다 낮다
- 갈음과 마감을 후보에서 빼면서 대장장이 메타포의 정확도는 살짝 양보했다. 의미 분리와 사용자 인지 부담을 우선했다
- ADR 0002의 결정 1(6단계로 확장)을 7단계로 확장한 셈이다. ADR 0002 본문은 보존하고, 같은 문서의 결과 절 또는 미래 묶임 절에 본 ADR로 갱신됐다는 한 줄을 추가한다. 역사를 다시 쓰지 않는다는 워크로그 원칙을 ADR에도 같은 결로 적용한다

### 미래 묶임
- 새 단계 이름 set, 한국어 세움, 별칭 set은 표준이다. 다른 단어로 변경하려면 별도 ADR이 필요하다
- 세움이 다듬과 비춤 사이라는 위치도 표준이다. 다른 자리로 옮기려면 별도 ADR이 필요하다
- 세움 안에 들어갈 emit과 verify의 구체 동작(어떤 언어와 빌드 도구를 우선할지, .beoreum/ 산출물 형식)은 후속 작업에서 다룬다. 본 ADR은 단계의 존재와 책임만 정한다
- 7단계로 확장됐으니 새 단계 추가는 더욱 신중해야 한다. 8단계로 늘릴 결정은 ADR이 필요하고, 그 ADR은 비기술 창업자 인지 부담을 정량적으로 검토해야 한다
