# ADR 0016. Inspect 단계 6영역과 inspect-report.md 형식

- 상태: 채택
- 날짜: 2026-04-28
- 결정자: DevSmith

## 맥락

ADR 0006이 7단계 메타포의 마지막 자리로 비춤(Inspect)을 박았다. ADR 0007이 산출물 자리(`.byeorim/project/inspect-report.md`)를 박았다. MANIFESTO III장이 비춤의 의미를 정의했다. "빛에 비춰 결함을 보는 일이다. 보안, 성능, 운영, 확장성, 그리고 다시 시장의 관점까지. 여러 각도에서 한 번 더 본다."

ADR 0003 결정 3이 비춤 단계에 한 가지 자리를 더 추가했다. "Inspect 단계 또는 출시 직전 + 법적 리스크의 즉각 손해 항목"에 강한 신호를 사용한다. 평소 동행 톤을 유지하되 법적 리스크는 예외.

이번 ADR이 채울 자리는 다섯이다.

첫째, 비춤이 보는 영역의 구체적 정의. MANIFESTO의 큰 그림(보안/성능/운영/확장성/시장)을 받아 표준 영역 표로 박는다. 법적 리스크가 어디에 들어갈지도 결정.

둘째, 자동 생성의 깊이. forge/temper/set이 모두 deterministic skeleton을 만든 결을 따라 정적 체크리스트로 갈지, 프로젝트 데이터를 받아 영역별 맞춤 질문을 만들지, AI 기반 검수로 갈지.

셋째, 법적 리스크 영역의 강한 신호 표시. ADR 0003 결정 3이 "강한 신호"를 박았는데 그것이 markdown report에서 어떻게 보일지.

넷째, 시장 재검 영역과 prospect의 reality-check.md 사이 연결. 두 자리에서 같은 "시장"을 본다는 사실을 사용자에게 어떻게 알릴지.

다섯째, inspect 단계 종료 후 state.yml의 current_stage 처리. 다음 단계가 없는 마지막 단계라는 사실을 형식으로 어떻게 표현할지.

## 검토한 옵션

### 결정 1. 6영역의 구체적 정의

#### 옵션 A. 보안/성능/운영/확장성/법적 리스크/시장 재검 (이번 출시)
- 장점: MANIFESTO의 큰 그림(보안/성능/운영/확장성/시장)에 ADR 0003 결정 3의 법적 리스크 자리를 더한 6영역. 두 ADR의 결정이 한 자리에서 만난다. 출시 직전 강한 신호 자리(법적)가 명시적
- 단점: ADR 0003의 Reality Check 6영역과 다른 영역 표라 사용자가 두 표를 머리에 갖고 있어야 함. 다만 두 단계(prospect/inspect)가 다른 자리에서 다른 시각으로 보는 게 의도

#### 옵션 B. ADR 0003의 6영역(Reality Check)을 그대로 재사용
- 장점: 영역 표가 한 개. 학습 비용 낮음
- 단점: MANIFESTO가 비춤에서 명시한 "보안, 성능, 운영, 확장성"이 빠진다. 비춤이 시장 직시 한 번 더 보는 자리로만 좁혀짐. 메타포 충실도 약함

#### 옵션 C. ADR 0003 6영역 + 기술 4영역 = 10영역
- 장점: 모든 자리 망라
- 단점: 1순위 사용자(비기술 창업자)에게 압도. CLAUDE.md 섹션 0 위배

### 결정 2. 자동 생성의 깊이

#### 옵션 A. 정적 한국어 체크리스트(이번 출시)
- 장점: deterministic. 단위 테스트 결정성. forge/temper/set과 같은 결. 1순위 사용자가 바로 사용할 수 있는 체크리스트
- 단점: 프로젝트 맞춤이 약하다. 모든 프로젝트가 같은 질문을 받음

#### 옵션 B. 프로젝트 데이터 기반 맞춤 체크리스트
- 장점: 데이터베이스가 PostgreSQL이면 PostgreSQL 백업 전략 같은 구체적 질문
- 단점: 매핑 규칙이 복잡해진다. 미래에 새 옵션이 들어올 때마다 매핑이 늘어남. AI 어댑터 없이 휴리스틱으로는 품질이 안정적이지 않음

#### 옵션 C. AI 기반 검수
- 장점: 가장 깊은 자동 검수
- 단점: 실제 LLM 어댑터가 아직 없음. mock으로는 가짜 검수가 나옴. 검수의 품질이 사용자 출시 결정에 영향을 주는 자리라 가짜는 위험

### 결정 3. 법적 리스크 영역의 강한 신호 표시

#### 옵션 A. 영역 머리에 경고 인용구(blockquote)와 명시적 안내
- 장점: markdown 시각으로 구분. 사용자가 그 자리만 다른 자리와 다르게 본다. ADR 0003 결정 3의 의도가 형식에 박힌다
- 단점: 다른 영역과 형식이 다른 게 약간의 비대칭

#### 옵션 B. 평문 한 줄 안내(다른 영역과 같은 형식)
- 장점: 형식 일관성
- 단점: 강한 신호가 약하게 보임. ADR 0003 결정 3의 의도와 어긋남

#### 옵션 C. 별도 파일(legal-checklist.md)로 분리
- 장점: 다른 자리와 명확히 구분
- 단점: 한 자리에서 보던 것을 두 자리로 나눔. 사용자 인지 비용 증가

### 결정 4. 시장 재검과 reality-check.md 연결

#### 옵션 A. 시장 재검 영역에 reality-check.md 경로를 명시적으로 적고 다시 읽도록 안내
- 장점: 두 자리(prospect/inspect)가 같은 시장을 본다는 흐름이 명시적. 사용자가 출시 시점에 prospect 시점의 인식을 다시 본다
- 단점: reality-check.md가 placeholder인 동안에는 가리킬 자리가 비어있음. 다만 미래 출시에서 채워질 자리라는 안내 가능

#### 옵션 B. 시장 재검 영역에 자체 질문만 두고 reality-check.md 언급 없음
- 장점: 단순
- 단점: prospect와 inspect 사이 연결이 안 보임

### 결정 5. inspect 후 state.yml의 current_stage

#### 옵션 A. current_stage = 'done' (이번 출시)
- 장점: 7단계 완료가 명시적 신호. 다음에 어디로 가야 할지 사용자가 즉시 안다(나갈 자리). 미래에 status 명령어가 'done'을 인식해 "모든 단계 완료" 메시지를 보여줄 수 있음
- 단점: inspect 재실행하려면 state를 수동으로 'inspect'로 되돌려야 함

#### 옵션 B. current_stage = 'inspect' 그대로
- 장점: inspect 재실행이 자연스러움
- 단점: 7단계 완료 신호가 없음. completed_stages에 'inspect'가 들어있긴 하지만 current_stage 한 자리만 봐서는 끝났는지 모름

#### 옵션 C. current_stage 필드 자체를 삭제
- 장점: 종료 표시
- 단점: state.yml의 schema_version 1이 current_stage를 필수 필드로 박아둠. 마이그레이션 부담

## 결정

### 결정 1: 6영역 = 보안/성능/운영/확장성/법적 리스크/시장 재검 (옵션 A)

inspect의 표준 6영역은 다음과 같다. 각 영역의 의미와 책임이 박힌다.

1. **보안**: 인증, 권한, 데이터 보호, 입력 검증, 통신 암호화
2. **성능**: 응답 시간, 처리량, 캐싱, 데이터베이스 최적화
3. **운영**: 모니터링, 로깅, 배포, 백업, 사용자 문의 채널
4. **확장성**: 부하 증가 대응, 데이터 증가 대응, 비동기 처리
5. **법적 리스크**: 개인정보, 인허가, 미성년자 보호, 결제/환불 규정, AI 차별 (출시 직전 강한 신호 자리, ADR 0003 결정 3)
6. **시장 재검**: prospect의 Reality Check를 다시 본다. 시장이 그때와 달라진 자리, 첫 100명 모집 계획, 운영비, 같은 도메인 실패 사례

ADR 0003의 Reality Check 6영역(시장 포화/진입 비용/양면 시장/법적/수익/묘지)과 다른 영역 표다. 두 단계가 다른 시각에서 본다는 의도. prospect는 시작 전, inspect는 출시 직전.

### 결정 2: 정적 한국어 체크리스트 (옵션 A)

각 영역에 정적 한국어 질문 4~6개를 markdown checkbox(`- [ ]`)로 둔다. 모든 프로젝트가 같은 질문을 받는다. 프로젝트 맞춤 자동 생성과 AI 기반 검수는 미래 ADR로 미룬다.

forge/temper/set이 모두 deterministic skeleton을 만든 결과 같다. 한 자리(이번 출시)에 집중하고 다음 자리(미래 출시)로 확장하는 패턴.

### 결정 3: blockquote 경고 인용구 + 명시적 안내 (옵션 A)

법적 리스크 영역은 다른 영역과 시각적으로 구분된다. 영역 머리에 markdown blockquote(`>`)로 경고 인용구를 넣는다.

```markdown
## 5. 법적 리스크

> ⚠ 이 영역은 출시 직전 강한 신호 자리입니다(ADR 0003 결정 3). 사용자 데이터, 인허가, 미성년자 보호처럼 법령 위반 시 즉각적 손해가 발생하는 자리는 변호사 자문을 받으세요.

- [ ] ...
```

이모지 사용: ADR 0003 결정 3의 강한 신호 정신을 시각으로 살리기 위해 한 자리에 한 개 이모지 허용. CLAUDE.md 섹션 8의 "사용자 출력은 비기술 창업자가 이해할 수 있어야 한다" 정책 안에서, 한 이모지가 한국어 안내를 보강하는 자리.

### 결정 4: 시장 재검 영역에서 reality-check.md 경로 명시 (옵션 A)

시장 재검 영역은 prospect의 reality-check.md 경로를 명시적으로 안내한다.

```markdown
## 6. 시장 재검

prospect 단계에서 본 시장을 다시 봅니다. 만들기 시작했을 때와 출시 직전의 시각은 다릅니다.

`.byeorim/project/reality-check.md`를 다시 읽어보세요. 그때와 시장이 달라진 자리가 있나요?

- [ ] ...
```

reality-check.md가 placeholder인 동안에도 경로 안내는 의미가 있다. 미래 출시에서 reality-check.md가 채워지면 그 시점에 사용자가 자연스럽게 두 자리를 연결한다.

### 결정 5: current_stage = 'done' (옵션 A)

inspect가 완료되면 state.yml의 current_stage가 'done'으로 바뀐다. completed_stages에 'inspect'가 들어가서 7단계 모두 완료된 상태.

```yaml
schema_version: 1
created_at: 2026-04-28T...
current_stage: done
completed_stages:
  - prospect
  - smelt
  - shape
  - forge
  - temper
  - set
  - inspect
```

inspect 재실행을 원하면 사용자가 수동으로 state.yml의 current_stage를 'inspect'로 되돌린다. 미래에 reset 또는 redo 명령어 ADR이 들어오면 그 자리에서 자동화될 자리.

'done'은 stage 식별자가 아니라 종료 marker다. 다른 단계 코드는 'done'을 single_stage 비교에서 만나면 자연스럽게 단계 불일치로 거부한다.

## 결과

### 긍정적
- inspect의 6영역이 표준으로 박혔다. MANIFESTO와 ADR 0003 결정 3의 의도가 한 자리에서 만나 6영역이 됨
- 정적 체크리스트라 단위 테스트가 결정적이고 빠르다. forge/temper/set과 같은 결
- 법적 리스크의 blockquote 경고가 시각으로 강한 신호를 만든다. 사용자가 그 영역만 다르게 본다
- 시장 재검의 reality-check.md 참조가 두 단계(prospect/inspect)를 명시적으로 연결한다. 사용자가 시작과 출시 두 시점에 같은 시장을 본다는 흐름
- current_stage = 'done'이 7단계 완료 신호. 미래의 status 명령어가 자연스럽게 받아들일 자리
- 사용자가 markdown checkbox(`- [ ]`)를 그대로 사용하거나 다른 도구(GitHub issue, Notion 등)로 옮길 수 있음

### 부정적 / 트레이드오프
- ADR 0003의 Reality Check 6영역과 inspect의 6영역이 다른 영역 표라 사용자가 두 표를 머리에 갖고 있어야 한다. 다만 두 단계가 다른 시각이라는 의도가 그 분리에 박혀있음
- 정적 체크리스트는 프로젝트 맞춤이 약하다. PostgreSQL이든 SQLite든 같은 백업 질문을 받음. 미래 출시(프로젝트 맞춤 또는 AI 검수)가 보강
- 영역의 질문 갯수와 본문은 한 자리(코드)에 박혀있어 한국어 표현이 시간이 지나면서 다듬어질 자리. 카탈로그 진화 노트와 비슷한 자리에 추적
- current_stage = 'done'은 inspect 재실행을 막는다. 사용자가 수동으로 되돌려야 함. reset/redo 명령어가 미래 자리

### 미래 묶임
- 6영역 정의는 표준이다. 영역 추가/제거 또는 이름 변경은 ADR로 결정한다
- 정적 체크리스트는 schema_version 1의 표준. 프로젝트 맞춤 자동 생성은 별도 ADR로 도입
- AI 기반 검수는 별도 ADR. 실제 LLM 어댑터가 들어와야 가능
- 법적 리스크 영역의 blockquote 형식은 표준. 다른 강한 신호 자리(미래에 새 영역에서 강한 신호가 들어오면)도 같은 형식 사용
- current_stage = 'done' 종료 marker는 표준. 다른 종료 marker나 마지막 단계 자체를 바꾸는 결정은 ADR
- inspect 재실행 / reset / redo 명령어는 미래 ADR로 도입. 그 시점에 'done' 처리도 함께 결정

## 링크

- 후속 작업 후보: 프로젝트 맞춤 체크리스트 ADR, AI 기반 검수 ADR, reset/redo 명령어 ADR, status 명령어 ADR(done 인식)
- 관련 정책: CLAUDE.md 섹션 0(사용자 우선순위), 섹션 8(파일당 책임, 한국어 메시지), MANIFESTO III장(비춤 정의)
