# ADR 0043. block.path i18n 허용

- 상태: 채택
- 날짜: 2026-05-06
- 결정자: DevSmith
- 관계: ADR 0042(block.path 옵셔널 + 영문 id 정책)의 path 패턴 갱신. ADR 0041(REST path 복수형)의 자동 복수화 결은 그대로 영문만

## 맥락

ADR 0042가 block.path 옵셔널 필드를 박았다. 패턴은 `^/[a-z0-9/_{}-]+$`로 ASCII 영문만 허용. 결정 4(REST path 패턴)에서 한국어 path는 의도적으로 거부했다.

다만 두 자리에서 결이 어긋난다.

첫째, block.id는 ADR 0042 결정 1로 영문만 강제(자동 복수화가 안 깨지도록). 그런데 block.path는 사용자가 명시적으로 박는 옵셔널 자리. 사용자가 의도해서 한국어 path(`/주문`, `/예약-내역`)를 박고 싶다면 막을 이유가 약하다.

둘째, 모던 HTTP 프레임워크(Express, Fastify, FastAPI, Spring)는 UTF-8 path를 처리한다. URL 인코딩이 자동으로 일어나서 wire 자리에서는 `%EC%A3%BC%EB%AC%B8` 결로 가지만 코드와 사용자 시각에서는 `/주문`. 1순위 사용자(비기술 창업자)가 한국어 도메인을 만들 때 자기 언어로 path가 박히는 결이 자연스럽다.

ADR 0042 결정 4에서 미래 ADR로 풀어줄 자리라고 박아두었다. 이 ADR이 그 자리.

## 검토한 옵션

### 결정 1. 새 패턴 결

#### 옵션 A. negative pattern (위험한 char만 거부)
- 패턴: `^/[^\s?#\\<>"'`]+$`
- 장점: 한국어/일본어/중국어 등 모든 Unicode letters 허용. 위험한 자리(공백, URL 특수문자, HTML 위험)만 거부. 가장 유연
- 단점: 거부 자리가 char 단위라 사용자가 어떤 자리가 거부인지 한눈에 안 보임

#### 옵션 B. positive pattern (안전한 char + 명시적 Unicode 범위)
- 패턴: `^/[a-zA-Z0-9_{}/\\-가-힣一-鿿぀-ゟ゠-ヿ]+$`
- 장점: 명시적이라 보기 좋음
- 단점: 다른 언어(아랍어, 러시아어, 태국어 등)가 들어오면 패턴 갱신 자리. CLAUDE.md 섹션 0(글로벌 표준 비전) 정신과 약간 어긋남

#### 옵션 C. 패턴 자체를 제거(URL 안전은 forge가 책임)
- 장점: 가장 유연
- 단점: 사용자가 공백 들어간 path를 박으면 forge에서 URL 인코딩 자리에서 깨짐. 검증을 미루는 결

### 결정 2. 자동 복수화(pathFromBlockId)도 i18n 허용 자리

#### 옵션 A. 자동 복수화는 ASCII 영문만(현재 그대로). i18n은 block.path 명시 자리에서만
- 장점: 자동 복수화는 영어 명사 결만 처리. 한국어 id는 schema에서 거부되므로 어차피 일어나지 않음. 결이 일관
- 단점: 없음(자동 복수화 자리에 한국어가 들어올 자리가 처음부터 없음)

#### 옵션 B. 자동 복수화도 i18n 시도(예: 한국어 id가 들어오면 그대로 path)
- 장점: 결이 자유로움
- 단점: ADR 0042 결정 1로 block.id가 ASCII만이라 적용 자리가 없음. 과잉 설계

### 결정 3. 검증 시점

#### 옵션 A. catalog.schema.json의 block.path 패턴 갱신 한 자리만
- 장점: 검증이 한 자리에 모임. 다른 검증(forge 단계)에서 또 검증할 필요 없음
- 단점: 없음

#### 옵션 B. forge가 추가 런타임 검증
- 장점: 이중 안전망
- 단점: 검증 자리 두 곳. 결이 흩어짐

## 결정

### 결정 1: negative pattern (옵션 A)

block.path 패턴을 `^/[^\s?#\\<>"'`]+$`로 갱신. 거부되는 char.

- 공백류(`\s`): 공백, 탭, 줄바꿈
- URL 특수문자: `?`(query string), `#`(fragment)
- HTML 위험: `<`, `>`, `"`, `'`
- 백슬래시: `\\`
- 백틱: 마크다운/터미널에서 어색한 자리

허용되는 char.

- ASCII 영문, 숫자, 하이픈, 언더스코어
- 슬래시(`/`), 중괄호(`{`, `}`)
- 한국어, 일본어, 중국어, 아랍어, 러시아어 등 모든 Unicode letters
- 이모지도 기술적으로 허용(다만 권장 안 함)

### 결정 2: 자동 복수화는 ASCII만 그대로 (옵션 A)

pathFromBlockId는 영문 id에서 영문 path를 만드는 자리. block.id는 ADR 0042로 ASCII 영문만 허용되니 자동 복수화 자리에 한국어가 들어올 자리가 없음. 결이 일관.

i18n path를 원하는 사용자는 block.path를 명시적으로 박는 결.

### 결정 3: schema 자리 한 곳만 (옵션 A)

catalog.schema.json의 block.path pattern만 갱신. forge.js의 pathForBlock은 block.path를 그대로 사용(검증 안 함). schema가 안전망.

## 결과

### 긍정적
- 한국어 도메인을 만드는 1순위 사용자(비기술 창업자)가 자기 언어로 path를 박을 수 있는 자리(`path: /예약-내역`)
- 일본어/중국어 등 다른 언어 도메인도 같은 결로 풀린다. CLAUDE.md 섹션 0(글로벌 표준 비전) 정신
- ADR 0042의 미래 자리(i18n path)가 풀린다
- 위험한 char(공백, URL 특수문자, HTML 위험)는 여전히 거부되어 안전

### 부정적 / 트레이드오프
- URL 인코딩 자리에서 wire 결이 길어짐(`/주문` → `/%EC%A3%BC%EB%AC%B8`). 다만 사용자 시각에서는 한국어. API 클라이언트가 자동 인코딩
- 일부 오래된 API 클라이언트나 CLI 도구는 UTF-8 path를 못 다룰 수 있음. 다만 모던 도구는 모두 처리
- 이모지가 기술적으로 허용. 권장 안 함이라 카탈로그 작성자 결로 둠. 미래에 명시적 거부 자리는 별도 ADR
- block.path를 박는 사용자가 늘어나면 catalog.yml 자리 길이가 미세하게 자라남

### 미래 묶임
- block.path 패턴(negative regex)은 표준. 변경하려면 새 ADR
- 자동 복수화는 ASCII만이라는 결은 표준
- 이모지 거부 자리는 미래 ADR(피드백 쌓이면)
- 다른 곳(prospect import의 source path 같은 자리)에 i18n path가 박힐 때는 같은 결로 자라남

- 짝 결정: ADR 0041 (자동 복수화는 ASCII만 그대로)
- 동행 톤: ADR 0003 결정 2
