# ADR 0004. v0.1.0 마이그레이션 대신 신규 구현을 선택한 이유

- 상태: 채택
- 날짜: 2026-04-27
- 결정자: DevSmith

## 맥락

ADR 0001에서 프로젝트 이름을 Forge Protocol에서 Byeorim으로 변경했다. ADR 0002에서 5단계를 6단계로 확장하고 작업 어휘 체계를 새로 잡았다. ADR 0003에서 Reality Check 6영역과 동행 톤을 결정했다.

이 세 결정을 기존 코드베이스(Forge Protocol v0.1.0)에 적용할 수 있는지 검토했다. v0.1.0의 현재 상태는 다음과 같다.

- CLI 엔트리포인트: bin/forge.js
- 핵심 로직: lib/dependency.js(의존성 해결 엔진), lib/catalog.js(카탈로그 로더), lib/smelt.js(대화형 블럭 선택), lib/meta-smelt.js(적응형 설문 기반 카탈로그 생성)
- 데이터: templates/commerce/catalog.yml(22개 블럭, 19개 의존성)
- 구조: 단일 lib/ 폴더에 모든 코드가 섞여 있음. 멀티 모듈 아님
- 동작 확인: forge init과 forge status만 동작. smelt는 코드 작성 완료 후 대화형 테스트 미완
- 사용자: 0명. 외부 공개 전

변경이 필요한 항목을 전부 나열하면 다음과 같다.

파일명 변경: bin/forge.js, lib/meta-smelt.js, 생성되는 .forge/ 디렉토리 전체, forge-report.md. 디렉토리 구조 변경: 단일 lib/에서 packages/core, packages/catalog, packages/cli, packages/ai, packages/templates 5개 패키지로 분리. 명령어 변경: forge에서 byeorim으로, prospect 명령어 신설, 별칭 시스템 신설. 데이터 흐름 변경: meta-smelt가 독립 단계(prospect)로 승격되면서 입출력 흐름 재설계. 사용자 출력: 모든 메시지를 동행 톤으로 재작성. 신규 기능: Reality Check, 다이어리, 6단계 전체.

변경 비율을 추정하면 코드 70 ~ 80%, 구조 100%, 문서 100%이다. 마이그레이션 후 원래 코드로 남는 부분은 dependency.js의 순수 로직 일부와 catalog.yml 데이터 정도로, 전체의 20 ~ 30%에 불과하다.

## 검토한 옵션

#### 옵션 A. 마이그레이션 (v0.1.0을 고쳐서 벼림으로)

70% 이상을 뜯어고치면서 30%를 살리는 접근이다.

- 장점: 기존 Git 히스토리 유지. 작업한 코드를 버리지 않는 심리적 안전
- 단점: 새 구조에 옛 코드를 끼워 맞추는 과정에서 이상한 타협이 생긴다. 그 타협이 6개월 뒤 기술 부채가 된다. 단일 lib/ 구조를 5개 패키지로 분리하는 작업은 코드 이동 후 의존성 정리까지 해야 하므로 새로 짜는 것보다 느릴 수 있다. CLAUDE.md의 규칙을 소급 적용해야 하므로 코드 스타일이 섞인다. 커밋 히스토리가 리네임 커밋으로 채워져 포트폴리오 가치가 떨어진다

#### 옵션 B. 신규 구현 (v0.1.0은 아카이브, 새 구조에서 처음부터)

새 레포 또는 빈 브랜치에서 시작한다. v0.1.0에서 가져오는 것은 코드가 아니라 지식이다.

- 장점: CLAUDE.md가 첫날부터 살아있다. 첫 커밋부터 멀티 모듈 구조, 테스트, ADR, 워크로그가 자연스럽게 적용된다. 기술 부채 0에서 출발. 커밋 히스토리가 깨끗해 포트폴리오로서 더 인상적이다. 마이그레이션과 작업량이 비슷하거나 오히려 적다(끼워 맞추기 비용이 없으므로)
- 단점: v0.1.0의 동작하는 코드를 버리는 심리적 비용. dependency.js 알고리즘을 다시 짜야 하는 시간(다만 알고리즘을 이미 이해하고 있으므로 처음 짤 때보다 빠르다)

#### 옵션 C. 점진적 전환 (v0.1.0에서 시작하되 한 모듈씩 분리)

Strangler Fig 패턴. 구식 코드를 감싸는 새 레이어를 한 겹씩 씌운다.

- 장점: 언제든 중간 상태에서 동작하는 코드가 있다
- 단점: v0.1.0에 사용자가 0명이므로 중간 동작 상태의 가치가 없다. 두 구조(구식/신식)가 공존하는 기간 동안 메인테넌스 부담이 두 배다. 가장 느린 경로

## 결정

옵션 B를 채택한다. v0.1.0은 아카이브로 보존하고, 새 구조에서 처음부터 만든다.

v0.1.0에서 가져오는 것은 세 가지이다.

첫째, dependency.js의 의존성 해결 알고리즘(resolveRequired, resolveAll, collectDecisions). 파일을 복사하는 게 아니라 알고리즘을 이해한 뒤 packages/core에 맞게 처음부터 짠다. 순수 함수로 분리하고 단위 테스트를 90% 이상 붙인다.

둘째, templates/commerce/catalog.yml의 22개 블럭, 19개 의존성 데이터. 데이터이므로 구조만 .byeorim/ 형식에 맞춰 재배치한다. 코드 변경 없음.

셋째, docs/spec.md의 상세 명세 내용. 용어를 벼림 정체성에 맞게 갱신한 뒤 가져온다.

v0.1.0의 아카이브는 legacy/forge-protocol-v0.1 브랜치로 보존한다. 삭제하지 않는다. 새 구현에서 알고리즘 참고가 필요할 때 줄 단위로 대조할 수 있어야 한다.

옵션 C(점진적 전환)를 택하지 않은 결정적 이유는, v0.1.0에 사용자가 0명이라는 사실이다. 사용자가 있으면 호환 모드를 유지해야 하지만, 지금은 아무도 다치지 않는다. 비용이 가장 적을 때 구조를 바꾸는 게 맞다.

## 결과

### 긍정적
- 기술 부채 0에서 출발한다
- CLAUDE.md 섹션 2(절대 금지선), 섹션 3(멀티 모듈), 섹션 4(테스트)가 첫날부터 적용된다
- ADR-0001부터 코드가 자라는 과정이 벼림의 역사 요구사항(섹션 5)을 실천하는 여정이 된다
- 커밋 히스토리가 깨끗해 포트폴리오 가치가 높다
- dependency.js를 다시 짜는 과정에서 알고리즘에 대한 이해가 더 깊어진다

### 부정적 / 트레이드오프
- v0.1.0의 동작하는 코드를 버리는 심리적 비용이 있다. 코드를 만든 사람에게 이건 작은 비용이 아니다
- dependency.js 알고리즘 재구현에 시간이 든다. 다만 알고리즘을 이미 이해하고 있으므로 처음 짤 때의 절반 이하로 추정한다
- v0.1.0의 Git 히스토리(커밋, 브랜치)가 새 레포에서 끊긴다. 아카이브 브랜치로 보존하지만 연속성은 사라진다

### 미래 묶임
- 이 결정 이후 v0.1.0 코드를 새 레포에 직접 복사(파일 단위 복붙)하지 않는다. 알고리즘을 이해한 뒤 새 구조에 맞게 재구현한다
- catalog.yml 데이터만 예외적으로 직접 가져온다
- legacy/forge-protocol-v0.1 브랜치는 삭제하지 않는다. 최소 1년간 보존한다
