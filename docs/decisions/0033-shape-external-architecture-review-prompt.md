# ADR 0033. Shape 외부 아키텍처 검토 프롬프트

- 상태: 채택
- 날짜: 2026-05-05
- 결정자: DevSmith
- 관계: ADR 0030의 결을 shape에 옮긴다. ADR 0032의 reasons 두 시점과 picker user 시점 노출은 그대로 유지. ADR 0028의 외부 프롬프트 경로 결을 따름
- 명세 갱신: [docs/specs/architecture-recommendation.md](../specs/architecture-recommendation.md)

## 맥락

ADR 0032가 shape에 AI 추천과 검토 흐름을 박았다. 추천 이유는 두 시점({user, dev})으로 적히고 picker는 user 시점만 노출, dev 시점은 후속 부산물 자리에서 노출한다고 약속했다. 그 후속 자리가 이번 ADR이다.

smelt가 이 결을 ADR 0030에서 외부 검토 프롬프트(`block-review-prompt.md`)로 풀었다. 사용자가 외부 AI(Claude.ai/ChatGPT/Gemini)에 마크다운을 그대로 붙여넣어 자기 도메인을 더 자세히 검토받는 자리. shape에도 같은 결이 비어있다.

shape의 4개 결정(language, database, api_style, architecture_pattern)은 ADR 0012의 표준 옵션 안에서만 고른다. 표준 옵션은 12개(3+4+3+3). 비기술 창업자 1순위 사용자는 그 12개 중 어느 하나를 골라도 그 자리가 자기 도메인에 어울리는지 판단할 도구가 부족하다. picker의 [추천] 라벨과 user 시점 한 줄로는 한계가 있다.

외부 AI에 자기 도메인과 4개 결정을 한꺼번에 보여주고 "이 결정이 도메인에 어울리는가, 트레이드오프는 무엇인가, 더 가벼운/무거운 결이 있는가"를 자세히 묻는 자리가 그 한계를 풀 수 있다. 부산물은 사용자가 응답을 읽고 architecture.yml을 수동으로 다듬거나 shape를 다시 돌리는 자리로 간다.

## 검토한 옵션

### 결정 1. 부산물 생성 시점

#### 옵션 A. shape가 끝나면 항상 자동 생성
- 장점: 사용자가 부산물 존재를 잊지 않음. smelt의 `block-review-prompt.md`와 같은 결. CLI 출력에 안내 한 줄로 흐름 자연스러움
- 단점: 사용자가 안 쓰면 디스크 자리만 차지. 다만 마크다운 한 파일이라 무게 작음

#### 옵션 B. 별도 명령 `beoreum shape review-prompt`
- 장점: 사용자가 원할 때만 생성
- 단점: 사용자가 새 명령을 알아야 함. 비기술 창업자에게 학습 비용. ADR 0028과 ADR 0030이 이미 자동 생성으로 갔는데 shape만 다른 결이면 일관성 깨짐

#### 옵션 C. 사용자에게 매번 묻기
- 장점: 사용자 의지 반영
- 단점: 흐름이 길어짐. 동행 톤 정신과 어긋남(매번 멈춰 물음)

### 결정 2. 프롬프트 정보 범위

#### 옵션 A. 7항목 + 카탈로그 전체 + 선택 블럭 + 4개 결정과 12개 표준 옵션 표 + 추천 두 시점
- 장점: 외부 AI가 사용자 도메인과 가능한 모든 옵션을 한 자리에서 보고 깊이 있게 검토. ADR 0030의 카탈로그 전체 담기 결과 같은 결. 외부 AI가 "다른 자리 X도 어울려 보여요" 같은 안내를 줄 수 있음
- 단점: 프롬프트 길이가 큼. 사용자가 외부 AI 컨텍스트 한도를 넘길 가능성. 다만 카탈로그 30~50 블럭 정도면 무리 없음

#### 옵션 B. 4개 결정과 사용자가 고른 블럭만 (가볍게)
- 장점: 프롬프트가 가벼움
- 단점: 외부 AI가 도메인 전체 시각을 못 봄. 카탈로그의 다른 블럭이 4개 결정에 영향을 줄 수 있는데 그 자리가 비어있음. ADR 0030의 결과 다른 결이라 일관성 깨짐

#### 옵션 C. 카탈로그는 빼고 7항목 + 선택 블럭 + 4개 결정만
- 장점: 옵션 A와 옵션 B의 중간 무게
- 단점: 옵션 B와 같은 단점. 카탈로그 빼면 외부 AI가 사용자 도메인의 다른 후보 자리를 못 봄

### 결정 3. 검토 요청 항목

#### 옵션 A. 도메인 적합성 + 트레이드오프 + 시작 무게 (smelt 결)
- 장점: smelt의 ADR 0030 검토 항목 셋과 같은 결. 사용자가 두 단계에서 같은 검토 결을 따라가 학습 비용 작음
- 단점: 항목이 셋이라 응답이 길어질 수 있음

#### 옵션 B. 트레이드오프만 좁게
- 장점: 응답이 짧음
- 단점: 도메인 적합성 자리가 빠짐. 외부 AI가 "이 결정이 카페 사장님 도메인에 잘 맞나"를 짚을 자리가 없음

#### 옵션 C. 자유 형식
- 장점: 외부 AI가 자기 결로 답함
- 단점: 사용자가 받는 응답 결이 매번 달라 일관성 떨어짐. 비기술 창업자에게 어디를 봐야 할지 막막

### 결정 4. dev 시점 노출

#### 옵션 A. 부산물에 user/dev 둘 다
- 장점: 외부 AI가 사용자 시점과 개발자 시점 둘 다 보고 검토. 시니어 개발자(3순위 사용자)가 외부 AI의 응답을 dev 시점으로 받을 수 있음. ADR 0030 결정 2(picker는 user만)와 일관
- 단점: 부산물 길이가 약간 늘어남

#### 옵션 B. user 시점만
- 장점: 일관성(picker와 같은 결)
- 단점: 개발자가 외부 AI에 검토 부탁할 때 기술 한 줄을 못 봄. ADR 0030이 dev를 부산물에 넣은 결과 어긋남

#### 옵션 C. dev 시점만
- 장점: 외부 AI가 기술 검토에 집중
- 단점: 비기술 창업자가 부산물 응답을 못 읽음. 1순위 사용자 정신과 어긋남

## 결정

### 결정 1: 자동 생성 (옵션 A)

shape의 ask → confirm → proceed 자리에서 architecture.yml을 작성한 직후 항상 부산물을 생성한다. 위치는 `.beoreum/project/prompts/architecture-review-prompt.md`. smelt의 `block-review-prompt.md`와 같은 디렉토리, 같은 결.

### 결정 2: 카탈로그 전체 + 4개 결정과 12개 표준 옵션 표 + 추천 두 시점 (옵션 A)

부산물에 다음 자리를 모두 담는다.

- 사용자 7항목 답변(intent.yml의 user_answers)
- 카탈로그 전체 blocks (id/name/user_desc/priority)
- 사용자가 고른 블럭(selected-blocks.yml의 selected/auto_added)
- 4개 결정과 사용자 선택값
- 4개 결정의 12개 표준 옵션 표(외부 AI가 다른 옵션도 비교할 수 있도록)
- AI 추천 두 시점({user, dev})

ADR 0030의 카탈로그 전체 담기 결과 같은 결이라 일관성이 박힌다.

### 결정 3: 도메인 적합성 + 트레이드오프 + 시작 무게 (옵션 A)

외부 AI에게 다음 셋을 묻는다.

1. 도메인 적합성: 4개 결정이 사용자 도메인(카페 사장님/학원 원장님 등)에 잘 맞는가
2. 결정 사이 트레이드오프: 4개 결정이 서로 어떻게 영향을 주는가(예: PostgreSQL과 GraphQL 조합의 트레이드오프)
3. 시작 무게: 지금 4개가 너무 무거운지/가벼운지. 더 어울리는 결이 있다면 안내

smelt의 ADR 0030 검토 항목 셋(잘 맞는 부분, 비어있는 자리, 시작 무게)과 결이 같다. 다만 shape의 자리에 맞춰 항목 이름을 다듬는다.

### 결정 4: 부산물에 user/dev 둘 다 (옵션 A)

부산물의 추천 자리에 두 시점을 모두 담는다.

```
- language: node
  - 일반 사용자 시점: ...
  - 개발자 시점: ...
```

picker는 ADR 0032 결정 2 그대로 user만 노출. 부산물은 외부 AI에 보내는 자리이므로 두 시점 둘 다 가치 있음.

## 결과

### 긍정적
- 4개 결정 앞 막막함이 picker의 [추천]만으로 풀리지 않을 때 외부 AI에 자세히 검토받는 자리가 생김
- 부산물 자동 생성으로 사용자가 흐름을 멈추지 않고도 검토 자리를 손에 쥠
- 카탈로그 전체와 12개 표준 옵션 표를 함께 보내 외부 AI가 다른 옵션과 비교한 검토를 줄 수 있음
- ADR 0030의 부산물 결과 같은 결이라 사용자가 두 단계에서 같은 사용 패턴을 따라감
- dev 시점이 부산물에 함께 들어가 시니어 개발자(3순위 사용자)가 외부 AI 응답을 자기 결로 받음

### 부정적 / 트레이드오프
- 부산물 마크다운이 매번 자리잡음. 사용자가 안 쓰면 디스크 자리만 차지
- 카탈로그가 큰 도메인(blocks 50+)에서는 프롬프트 길이가 부담될 수 있음. 사용자 피드백 받으면 truncation 자리 검토(후속 ADR)
- 12개 표준 옵션 표가 ADR 0012와 ARCHITECTURE_CHOICES 코드, claude system 프롬프트, 그리고 부산물 셋에 같은 자리가 박힘. 한 자리(ARCHITECTURE_CHOICES) 변경 시 세 자리 모두 봐야 함. 셋이 한 데이터에서 합성되는 결로 가야 일관성 유지

### 미래 묶임
- `architecture-review-prompt.md` 위치(.beoreum/project/prompts/)와 마크다운 형식은 표준
- 부산물에 담는 정보 범위(7항목 + 카탈로그 + 선택 + 4개 결정 + 추천)는 표준. 변경하려면 새 ADR
- 부산물에서 외부 AI에 묻는 검토 항목 셋은 표준. 항목 추가/제거는 새 ADR
- 부산물 응답을 다시 import하는 자리(예: `beoreum shape import-architecture-review`)는 미래 ADR에서 결정. 이번 출시는 사용자가 응답을 읽고 수동으로 다음 결정에 반영
