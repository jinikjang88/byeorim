## 배운 점

forge ADR 0023의 결을 그대로 옮기니 temper 어댑터 통합이 자연스러웠다. extractSchema가 두 자리(mock generic placeholder + claude 도메인 추론)로 갈라진 결을 fillTestCode도 그대로 따라간다(mock 언어 무관 의도 + claude 언어별 프레임워크 코드). 두 어댑터의 책임 분리가 같은 결로 박혀 사용자가 한 번 익히면 두 번째 자리에서 같은 시각을 적용할 수 있다.

runTemper가 architecture.yml을 처음 읽는 자리가 됐다. forge처럼 옵셔널 자리(어댑터 없으면 안 읽음)로 두니 후행 호환이 자연스럽다. `existsSync(archFile)` 가드로 architecture.yml이 없을 때도 graceful. catalog.yml도 같은 결로 옵셔널(블럭 도메인 정보가 있으면 어댑터에 전달, 없어도 안전).

mock의 GWT 텍스트 인용에서 `${given}을 준비하고`처럼 조사가 어색해졌다(`을`이 받침 없는 텍스트 뒤에 붙으면 `를`이 자연스러움). 한국어 조사 자동 처리는 미래 자리. 이번 출시는 결정성과 결을 우선.

claude 어댑터의 메서드가 일곱이 됐다(extractIntent, generateCatalog, generateRealityCheck, recommendBlocks, recommendArchitecture, extractSchema, fillTestCode). 인터페이스가 자라면서 한 자리에서 변경이 다른 자리에 영향을 안 주는 결이 살아남았다. 객체 인자 패턴과 옵셔널 메서드 결정 둘이 같이 작용한 결과.

runTemper와 interactiveTemper가 buildScenarios를 공유하도록 입력 로딩(loadTemperInputs)과 빌드 본체(buildScenarios), 산출물 합성(buildScenariosDoc), 디스크 쓰기와 advance(writeScenariosAndAdvance)를 잘게 쪼갰다. forge.js와 같은 결. 한 함수가 한 자리만 책임지니 interactiveTemper가 build → confirm 루프 안에서 buildScenarios만 다시 부르고 proceed에서만 합성+쓰기를 한 번 한다. redo 안에서는 디스크에 안 쓴다(forge의 결과 같음). 이게 의미 있는 자리. 사용자가 redo를 선택했을 때 산출물이 갱신되지 않은 채 다음 라운드로 가니 부분 상태가 디스크에 남지 않는다.

검토 화면에 시나리오 종류(happy_path)를 표시하는 결을 박았다. 이번 출시는 한 endpoint당 시나리오 1개라 한 줄로 보이지만 미래에 에러/엣지 시나리오가 들어오면 같은 endpoint 줄에 여러 줄로 펼쳐지는 결로 자연스럽게 자란다. formatScenarioBlockLines가 [first, ...rest]로 풀어 나눈 자리. 미래 자리를 위한 결이 지금 한 줄 안에 박혔다.

interactiveTemper의 어댑터 안내가 forge보다 한 결 더 묶였다. forge는 `!adapter || !adapter.extractSchema` 두 갈래만 봤는데 temper는 `!architecture`까지 묶어 한 자리에서 안내한다. architecture.yml이 없으면 어댑터를 가져도 fillTestCode를 못 부르는 결이라 같은 안내 자리. forge의 결을 그대로 따라가지 않고 temper 자체의 입력 의존성(architecture.yml)을 살린 자리.

mock의 결정성 안내 문구가 forge에서는 "schema가 다시 채워질 거예요"였고 temper에서는 "test_code가 채워질 거예요"로 한 자리만 다르다. 두 곳에 결정성 어댑터 명단을 박아두니 같은 결의 두 안내가 자연스럽게 살아난다. 미래에 어댑터 인터페이스에 isDeterministic 플래그가 박힐 자리 한 곳이 더 분명해졌다.

contracts와 시나리오를 함께 부산물에 담는 결정이 처음에는 중복처럼 보였다. forge 부산물에서 이미 contracts를 한 번 외부 검토 자리에 담았다. 다만 두 부산물이 묻는 질문이 다르다. forge는 "schema가 도메인에 맞는가"를 묻고 temper는 "test_code가 도메인에 맞는가"를 묻는다. 외부 AI가 test_code를 검토할 때 schema가 함께 보여야 "이 schema에 quantity 필드가 있는데 test_code에서는 안 검증해요" 같은 안내가 나온다. 두 부산물이 서로 다른 시각으로 같은 자료를 보는 결이라 중복이 아니라 보강.

loadTemperInputs가 점점 자랐다. 처음 PR 1에서는 contracts/architecture/catalog 셋만 읽었는데 PR 3에서 intent와 selected-blocks까지 더 읽는다. 다섯 입력 자리. 다만 한 함수에 모여있어 inputs.X로 한 자리에서 꺼내 쓰기 좋다. forge.js의 loadForgeInputs와 같은 결이 자연스럽게 자란다. 미래에 set 단계가 같은 입력 패턴을 따라가면 같은 결의 loadSetInputs 자리가 박힐 자리.

부산물이 redo 자리에서는 안 만들어지고 proceed 자리에서만 한 번 만들어지는 결이 forge와 같다. 사용자가 redo로 다시 만들어도 부산물은 마지막 라운드의 시나리오로 한 번만 갱신된다. 디스크에 부분 상태가 남지 않는다. interactiveTemper 자리의 build → confirm 루프 안에서 build만 다시 부르고 proceed에서만 합성+쓰기를 한 번 하는 결이 살아남았다.

bin/beoreum.js의 temper 핸들러가 forge 핸들러와 같은 결로 자랐다. AI가 채웠는지 안내 한 줄 + 부산물 안내 한 줄 + 다음 단계 안내. 사용자가 두 단계에서 같은 출력 패턴을 만난다.

테스트 자리에서 forge가 만드는 path 결을 한 번 더 익혔다. block 'order' → path '/order' (싱글, pathFromBlockId가 block.id를 그대로 path로). 처음에는 RESTful '/orders'(복수)일 거라고 가정하고 테스트를 짰는데 forge.js 본체가 단수형으로 박혀있었다. 테스트를 forge의 결에 맞춰 고쳤다. 단수/복수는 별도 결정이 필요한 자리(미래 ADR — 사용자가 path를 직접 다듬고 싶을 때).

응답 형식 안내 섹션이 검토 프롬프트 안(─── 사이)에 들어간 결이 옳다. 외부 AI가 보는 자리이므로 마커 안. 마커 밖은 사용자만 보는 자리. 두 독자(외부 AI와 사용자)의 결이 마커 한 줄로 갈라진다.

graceful degrade의 한 자리에서 사용자에게 안내하는 메시지가 두 결로 갈라진다. (1) "섹션을 못 알아봤어요" + (2) "외부 AI가 자유 형식으로만 답했거나 형식이 어긋났을 수 있어요" + (3) "응답을 직접 보시고 손으로 다듬으시거나 외부 AI에 형식대로 다시 답해달라고 부탁해주세요." 첫 줄은 사실 보고, 둘째 줄은 가능성 풀이, 셋째 줄은 사용자가 갈 수 있는 두 길. 동행 톤(ADR 0003 결정 2)의 결.

## 배운 점

OpenAPI 스펙은 단수/복수에 중립이지만 업계 관례(Microsoft/Google/Stripe/GitHub/PayPal/Twilio/Heroku)는 압도적으로 복수형. CLAUDE.md 섹션 1(프로덕션급 코드 품질)과 섹션 0(글로벌 표준 비전) 정신상 관례에 맞추는 결이 옳다. 1순위 사용자(비기술 창업자)는 path 결을 직접 못 보지만 만든 API를 받아 쓸 엔지니어가 어색해할 자리. 작은 default 한 자리지만 portfolio-grade 자리에서 의미가 크다.

pluralize 라이브러리(~2KB)가 commerce 카탈로그의 모든 block id를 자연스럽게 처리. 불규칙 자리(history → histories, search → searches, category → categories)도 한 자리에서 풀어줌. 직접 구현했으면 불규칙 표를 손으로 박아야 했고 미세한 자리에서 빈틈이 났을 것. 라이브러리 의존성 한 자리 추가로 풀린 자리가 깨끗.

하이픈 복합어를 마지막 단어만 복수화하는 결(`pluralizeSegment`)이 영어 명사 결과 자연스럽다. `cancel-return` → `cancel-returns`(returns만), `product-search` → `product-searches`(searches만), `order-history` → `order-histories`(histories만). 영어 명사구의 중심 단어가 보통 마지막에 오는 결이라 이 자리가 표준 복수화 자리.

비ASCII 폴백 결(`!/^[a-z][a-z0-9-]*$/.test(segment)`)이 한국어 block id에도 graceful하게 동작. 한국어 path는 URL 인코딩 자리가 따로 풀어야 하지만 forge가 깨지지 않는 결로 안전망이 있다. 카탈로그 작성자가 영문 id를 쓰는 결이 권장이지만 강제는 아니라는 결.

기존 forge-import 테스트를 PR 4(ADR 0039)에서 단수형(`/order`)으로 한 번 갱신했는데 PR 5(ADR 0041)에서 다시 복수형(`/orders`)으로 갱신하는 자리가 생겼다. PR 사이의 결이 바뀐 자리를 한 번 더 익혔다. 두 ADR이 한 묶음으로 결정됐으면 한 번에 풀 수 있었지만 결을 점진적으로 박는 결이 의도적이라 두 번 갱신은 자연스러움. 두 결이 평행이라 갈라서 풀리는 결.

`shipping → shippings` 같은 mass noun 자리가 살짝 어색하지만 pluralize가 일관되게 처리. 카탈로그 작성자가 mass noun을 명사형 id로 박는 결을 권장하면 됨(예: `shipment` 또는 `shipping-record`). 미래에 카탈로그 path override 옵셔널 필드가 생기면 사용자가 자기 결로 자리마다 푸는 자리.

## 배운 점

ADR 0041이 끝난 뒤 "사용자가 풀어야 한다"는 세션 5의 한 줄에 사용자가 멈춤 신호를 줬다. 개발자가 보는 사용자(catalog 작성자, 1순위 사용자, 신사업 개발자)를 가르지 않고 한 묶음으로 쓰면 비기술 창업자에게 부담이 옮겨가는 자리가 생긴다. 사용자를 갈라 보면 자리가 다르게 박힌다. 비기술 창업자는 카탈로그 안 만진다(받아 씀). mass noun 어색함은 카탈로그 작성자 자리. 한국어 ID는 외부 AI 책임. 1순위 사용자가 깨진 결을 만나는 자리는 외부 AI가 한국어 ID 카탈로그를 만들 때라는 결.

이 결을 따라 두 자리를 갈라 풀었다. (1) 카탈로그 작성자가 정밀 조정할 자리(block.path 옵셔널)는 스키마 한 자리 + forge 한 자리. (2) 1순위 사용자가 깨진 결을 만나는 자리는 두 단계로 막음. 외부 AI 프롬프트가 영문 id 강조(처음부터 안 만듦) + import 검증이 한국어로 풀어쓴 안내(만들어도 사용자가 다음 자리를 명확히 봄). 두 단계 자리가 평행이라 자연스럽게 안전망이 두 겹.

스키마가 이미 ASCII-only id를 강제하고 있었다는 자리(`^[a-z][a-z0-9-]*$` 패턴이 ADR 0005 시점에 박힘)는 큰 행운. 새로 검증 자리를 추가할 필요 없이 기존 자리에 메시지만 풀어쓰면 됐다. 다만 prospect-import의 기존 에러 메시지가 errors 배열의 객체를 `[object Object]`로 출력하는 자리였다(formatError 함수 없이 join하던 결). 이 자리도 세션 6에서 같이 풀어줬다(formatError로 `[kind] path message` 결로 풀어쓰기).

prospect-prompt에 두 줄을 더 박아 외부 AI의 결과 결을 형성. 외부 AI는 사용자가 한국어로 대화 중이라도 카탈로그는 영문 id로 답한다. 사용자가 한국어 id를 만나는 자리가 작아짐.

## 배운 점

생성기가 ep.method를 안 쓰고 OPERATION_HTTP_METHOD를 다시 매핑하던 결은 ADR 0044(singleton)가 들어오기 전에는 우연히 맞아떨어지던 자리. resource의 update가 PUT이라 OPERATION_HTTP_METHOD['update'] = 'put'이 정답. singleton이 들어오자 정답이 PATCH로 갈라지는 결이었지만 생성기는 PUT을 그대로 emit. 같은 결이 4번 반복된 자리(node/java/python/frontend 모두)라 단일 자리 버그가 아니라 패턴 자리.

forge가 ep.method를 박는 자리가 진실(source of truth)이라는 결을 생성기가 따라가도록 갱신했다. operation 이름은 의미 자리(create/list/get/update/delete/search)고, method 자리는 forge가 결정한 자리(POST/GET/PUT/PATCH/DELETE). 두 자리를 분리한 결이 옳다. 사용자(카탈로그 작성자)가 같은 operation 이름이지만 다른 method 결을 표현할 수 있는 자리가 살아남는다(미래에 import-review로 ep.method를 다듬는 자리도 그대로 동작).

path prefix(`/${blockId}` 하드코딩)도 같은 결의 자리였다. ADR 0041(복수형), ADR 0042(block.path), ADR 0043(i18n path)가 forge에서 박은 path 결을 생성기가 무시하던 자리. `endpoints[0].path`를 base로 사용하니 4 ADR이 모두 set 단계에 살아남는다. block.path가 `/me`면 prefix가 `/me`, ADR 0041로 자동 복수화된 `/orders`면 prefix가 `/orders`, 한국어 `/주문`이면 prefix가 `/주문`. 한 자리에서 모두 풀린다.

7단계 메타포의 자리가 의미 있게 풀렸다. prospect/smelt/shape/forge/temper는 야금술 자리(원료 다듬기). set은 건축 자리(다듬은 원료로 건물 세우기). temper에서 박은 method 결이 set의 건물에 그대로 emit되는 자리가 살아나야 메타포가 살아남는다. 이번 세션이 그 자리를 지킨 결.

util.js에 methodSpec 헬퍼를 둔 결이 4 생성기에서 같은 결로 사용되는 자리가 깨끗. 한 자리만 변경하면 4 생성기가 다 따라가는 결. 미래에 새 method(예: HEAD, OPTIONS)가 들어오면 한 자리에서 풀린다.

## 아직 열려있는 것

- Java/Python 생성기의 path param 추출은 한 자리만(`id`) 처리. 여러 path param(예: `/items/{itemId}/options/{optionId}`)은 첫 자리만 잡힘. 미래 자리지만 흔하지 않음
- pathPrefix를 endpoints[0].path로 박은 자리. 모든 endpoints가 같은 base를 가진다는 가정. forge는 그렇게 박지만 import-review로 사용자가 base가 다른 endpoints를 박을 수 있는 자리가 미래에 생기면 갱신 필요
- ADR 0044가 약속한 singleton 전용 GWT 템플릿(get_singleton/update_singleton/delete_singleton)은 여전히 미래 ADR 자리
- shape.js/smelt.js의 unused eslint-disable 두 자리는 여전히 cleanup 자리
- stage-helpers.js 추출도 여전히 cleanup 자리
