## 배운 점

sed로 일괄 치환을 박는 결이 53개 파일 영향이라 가볍지 않았다. 한 결로 풀린 자리들.

첫째, `docs/specs/reality-check.md`처럼 docs 안 명세 문서가 같은 이름을 가져 sed가 잘못 박혔다. 별도 `s|docs/specs/prospect-reality-check\.md|docs/specs/reality-check.md|g`로 되돌렸다. 미래에 비슷한 일괄 치환을 박을 때 "치환 대상이 같은 이름의 다른 결에 박혀 있지 않은가"를 먼저 보는 결.

둘째, 테스트 안 정규식 결(`/\.byeorim\/project\/reality-check\.md/`)이 첫 sed에 안 잡혔다. 백슬래시 이스케이프된 점 때문. 별도 패스로 `reality-check\\.md` 결을 처리. 미래에 정규식 결을 sed로 다룰 때 두 패스가 필요한 결.

셋째, `for f in $files; do sed ...` 결이 bash에서 변수 확장 결로 깨졌다. 결과적으로 sed가 한 번에 모든 파일을 인자로 받아 "File name too long"으로 멈춤. `grep -rln ... | while IFS= read -r f; do sed ... done` 결로 풀어 한 파일씩 처리. 미래에 비슷한 결을 박을 때 IFS 결을 명시적으로 두는 결.

ADR 0007에 보강 결을 한 줄로 안내한 결이 자연스러웠다. ADR을 새로 박으면 ADR 0007이 "잘못된 결"로 박힌 결이 아니라 "보강이 따라온 결". 결정 시점의 역사가 그대로 보존되고 미래 기여자가 0007을 읽다가 보강을 따라간다. supersedes(완전 대체)보다 약한 결로, ADR 0007의 다른 결정(루트 위치, 평탄 vs 서브디렉토리, 단계 진행 메타, 확장자)은 그대로 살아남는다.

공통 파일 결을 가른 결이 ADR 0058의 핵심이다. state.yml/decisions.yml/diary.md에 프리픽스를 박지 않은 결은 단계와 공통의 결을 명시적으로 분리한 결. inspect 단계가 이미 프리픽스 결을 가졌듯, 한 단계의 결과는 모두 프리픽스. 단계 사이에 공유되는 결은 평탄.

## 알아둘 것

- 코드 안 경로 문자열만 갱신. 실제 디스크 파일은 사용자의 `.byeorim/project/`에 있어 마이그레이션 결이 별도로 필요. 다만 0.x이라 외부 사용자 거의 없어 영향 작음
- sed 일괄 치환 후 한 곳을 잘못 박은 결(docs/specs/reality-check.md)을 별도 패스로 되돌림. 미래에 같은 결의 작업을 박을 때 영향 범위를 먼저 가르는 결
- 정규식 안 점 이스케이프(`\.md` 같은 결)는 sed 한 번으로 안 잡힘. 별도 패스로 정규식 결만 처리한 결을 기록
- bash for-loop의 변수 확장 결이 한 번에 깨지면 sed 인자 길이가 폭주. `while IFS= read -r` 결을 기본으로 박는 결이 자연스러움
- ADR 0058이 ADR 0007 결정 2만 보강한다는 한 줄 결을 0007 상태 줄에 박음. 미래 기여자가 0007을 읽다가 0058로 따라가는 결
