# Worklog — 2026-05-13

## 이번 세션의 목표

벼림을 사용자가 자기 머신에서 `byeorim` 한 단어로 부를 수 있게 박는다. 일단 로컬 install 결만(npm registry 정식 배포는 차후). 사용자가 어느 디렉토리에서나 `byeorim init`을 박을 수 있어야 외부 사용자 결의 진입 마찰이 한 결 줄어든다.

## 변경 사항

### 새 파일

- docs/decisions/0059-npm-local-install.md — 네 결정(symlink 결 1차, tarball 결 차후, private 유지, 메타데이터 박음)

### 손댄 파일

- README.md / README.en.md — "설치" 섹션 추가. git clone → npm install → npm install -g . 세 단계 박음. 어디서나 `byeorim` 결로 부를 수 있다는 안내

### 검증 결과

- `npm install -g .` 결로 글로벌 install 시도. 한 번에 통과
- `/opt/homebrew/bin/byeorim`이 워크스페이스 결 그대로 symlink로 박힘 → `/opt/homebrew/lib/node_modules/byeorim` → 클론한 저장소 결

- npm pack --dry-run 결로 tarball 시뮬레이션 — 208개 파일, 2.2MB. 다만 tarball 결로는 워크스페이스 의존성을 못 풀어 글로벌 install이 깨짐. 정식 결은 차후
- 코드 변경 없음. 기존 727 테스트 그대로

## 배운 점

`npm install -g .` 결이 workspace 모노레포에서 의외로 깨끗하게 박혔다. npm이 글로벌 결로 패키지를 복사하지 않고 클론한 저장소를 글로벌 결로 symlink. 그 결로 워크스페이스 의존성(node_modules 안 @byeorim/cli, @byeorim/ai 등)이 살아서 작동한다. 사실상 `npm link`와 같은 결이지만 한 명령으로 끝.

이 결의 트레이드오프 자리. 저장소를 옮기거나 지우면 글로벌 `byeorim`도 따라 깨진다. 정식 결은 npm registry 배포로 tarball을 사용자 머신의 글로벌 결에 동봉하는 결이 자연스럽다. 다만 워크스페이스 의존성을 동봉(`bundleDependencies`)하는 결을 박아야 하고, npm registry는 이름 선점/버전 비가역 결이라 이른 결로 박는 게 위험하다. 1차로 symlink 결만 박고 정식 결은 별도 ADR로 미루는 결이 합리적.

`npm pack --dry-run` 결로 208개 파일 2.2MB tarball이 만들어졌다. 이 결로는 워크스페이스 의존성이 동봉 안 돼 글로벌 install 시 `@byeorim/cli` 결을 못 찾는다. 미래 정식 결을 박을 때 `files` 필드와 `bundleDependencies` 결을 함께 박는 결.

ADR 0059에서 옵션 셋(symlink만 / 정식 npm publish / tarball만)을 갈라본 결과 1차 결로는 symlink가 가장 안전하다. 정식 publish는 비가역 결이 많고, tarball 단독 결은 정식 publish 작업의 거의 모든 결을 박아야 한다. 1차 결로 사용자 결을 한 결 본 뒤 정식 결로 가는 결이 자연스럽다.

bin 파일이 npm install 후 0644 → 0755로 mode가 바뀐 결을 봤다. npm이 bin 파일을 자동으로 executable로 만든다. git에는 0644로 두고 npm install이 0755로 박는 결이 표준. 이번에 잠깐 0755가 git diff에 보였는데 chmod 644로 되돌렸다. 미래에 install 결을 다시 시험할 때 같은 결이 다시 보일 자리. git diff에서 mode-only 변경은 무시하는 결.

## 해야 할 일

- 정식 npm registry 배포 결을 ADR 0060(예상)에서 박는다. 그때 bundleDependencies, files, private: true 풀기, npm 이름 선점 결을 함께 봄
- 정식 결 박기 전에 `byeorim`이 npm registry에서 비어있는지 확인. 차후 결
- 사용자가 글로벌 install 후 자기 프로젝트에서 전체 흐름(prospect → smelt → shape → forge → temper → set → inspect) 한 번 돌려 정합 결 확인

## 추천

- 1차 결로 사용자 결을 본 뒤 외부 신호(이슈, PR, 사용 후기)가 들어오면 그때 정식 결로 진입. 외부 신호 없이 정식 publish는 이른 결
- README 설치 결을 한 묶음 PR로 박는 결이 자연스러움. ADR 0059로 결의 근거를 박고, 정식 결은 별도 ADR로 미루는 결을 명시
- 글로벌 install 결이 symlink라는 결을 README가 안내. 사용자가 저장소를 옮기지 않게 하는 결

## 알아둘 것

- `npm install -g .`은 사실상 `npm link` 결. 글로벌 `byeorim` → 클론한 저장소의 bin/byeorim.js로 symlink가 박힘
- 사용자가 저장소를 지우거나 옮기면 글로벌 `byeorim`도 깨진다. README에 안내 한 줄 박음
- tarball 결로는 동작 안 함. `npm pack` → `npm install -g <tgz>` 결로 시험하면 워크스페이스 의존성을 못 풀어 `Cannot find package '@byeorim/cli'` 결로 깨짐. ADR 0059가 결을 설명
- private: true 유지로 `npm publish` 결이 자동 차단된다. 정식 결을 박을 때 별도 ADR로 풀음
- bin 파일이 npm install 후 자동으로 0755가 된다. git에는 0644로 두는 결이 표준
- 메타데이터 결(homepage, repository, bugs, keywords)을 미리 박았다. 정식 publish 결을 박을 때 따로 박을 결 줄어듦

## 배운 점

PR 1(2026-05-09)에서 4개 프롬프트(shape/forge/temper/inspect)에 예시 응답을 박았지만 prospect의 catalog-prompt가 빠진 결이 오늘 드러났다. 사용자가 "smelt는 OK였다"고 보고한 결이 의미하는 자리는 smelt의 review-prompt였지 prospect의 catalog-prompt가 아니었다. 두 프롬프트가 다른 결인데 한 묶음으로 본 결이 미스. 미래에 비슷한 작업을 박을 때 6개 프롬프트 결(prospect catalog + smelt review + shape review + forge review + temper review + inspect review)을 모두 명시적으로 가르는 결.

catalog-prompt의 결이 특히 까다로운 자리. 한 응답에 worlds/blocks/dependencies/cascades/prerequisites 다섯 결을 모두 담아야 하고, 각 결마다 필드 결이 다르다(예: cascade는 trigger + ask_questions, prerequisite는 name + enables). 추상 스키마만으로는 외부 AI가 결을 따라가기 어렵다. 한 곳에서 모든 결을 채운 예시가 가장 효과적.

cascade.ask_questions의 결이 가장 자주 깨질 자리. 사람이 보면 "질문 문자열 배열"이 자연스러운데 스키마는 `{question, options?, cascade_effects?}` 객체를 요구한다. 외부 AI가 사람의 결을 따라가 문자열로 박는 결이 합리적이지만 스키마와 어긋난다. 예시에 한 줄 강조(`반드시 객체 결로 박아주세요. 문자열 결은 거부됩니다`)를 박아 결을 잡음.

사용자의 깨진 catalog.yml을 즉시 fix하는 결을 9줄 node 스크립트로 풀었다. `js-yaml`로 load → 변환 → dump. 백업(.bak)을 미리 박은 결이 안전. 미래에 사용자가 비슷한 결로 부딪히면 `byeorim catalog repair` 같은 명령으로 박는 결도 검토 자리. 다만 외부 AI가 결을 잘 따라가도록 예시를 박는 결이 우선.

## 세 번째 세션의 목표

사용자가 외부 AI에 smelt review를 받았는데 응답이 순수 YAML 결로 박혔다(마크다운 헤딩 없음). 파서가 `## 제안된 변경 사항` 헤딩을 찾는 결이라 깨졌다. 어제 catalog의 ask_questions 결과 같은 패턴. 외부 AI가 형식 안내를 일부 건너뛰는 결.

파서를 더 관대하게 박는 결로 풀음. 마크다운 결을 못 찾으면 입력 전체를 순수 YAML로 시도하고, `changes:`(또는 `findings:`) 키가 박혀있으면 그대로 받는다.

## 변경 사항

### 손댄 파일

- packages/cli/src/review-response-parser.js
  - `tryParseRawYaml(markdown, expectedKey)` 헬퍼 한 결 추가. 입력 전체를 YAML로 시도해 expectedKey 배열을 뽑고, 깨지면 null 반환
  - `parseReviewResponse`: 마크다운 헤딩 못 찾으면 raw YAML 결로 폴백. `changes` 키가 박혀있으면 그대로 받음. 폴백도 깨지면 보강된 에러 메시지(\"순수 YAML 결로 답하려면 changes: 키로 시작하는 결로 박아주세요\")로 안내
  - `parseFindingsResponse`: 같은 결로 `findings` 키 폴백
- tests/unit/cli-review-response-parser.test.js — raw yaml 결의 정상 통과와 폴백 안내 결을 검증하는 테스트 3개 추가(changes 2개, findings 1개)

### 검증 결과

- npm test 731개 통과(기존 728 + 신규 3)
- ESLint 0 에러
- Prettier 통과
- 사용자 원본 `.byeorim/project/smelt-review.yml`(순수 YAML)로 `byeorim sml import-review` 정상 동작. 4개 변경 picker 정상 표시

## 배운 점

외부 AI가 형식 결을 일부 건너뛰는 결이 반복 패턴이다. 어제 catalog의 ask_questions 결(객체 → 문자열), 오늘 review response 결(마크다운 wrapper 생략). 두 결 모두 사람이 보면 자연스러운 결인데 스키마/파서가 결을 더 좁게 박은 자리. 두 갈래로 풀 수 있다.

- 갈래 1: 프롬프트에 예시를 더 강하게 박아 외부 AI가 결을 정확히 따라가도록(어제 PR #7의 결)
- 갈래 2: 파서/검증을 더 관대하게 박아 사용자 부담을 줄이는 결(이번 PR의 결)

두 갈래는 보완 관계. PR #7로 외부 AI 결의 정확도를 한 결 올리고, 이번 PR로 그래도 깨지는 결을 받아주는 결을 박았다. 미래 사용자가 같은 결로 부딪힐 가능성이 두 갈래 모두에서 줄어듦.

raw YAML 폴백 결을 박을 때 `try/catch`로 yaml load 실패를 흡수하는 결이 자연스러웠다. js-yaml이 던지는 결을 사용자에게 노출하지 않고 마크다운 결 안내로 폴백. 결의 결정성이 높아진다.

폴백 에러 메시지를 한 줄 더 박은 결(\"순수 YAML 결로 답하려면 changes: 키로 시작하는 결로 박아주세요\")이 다음 사용자에게 결을 안내한다. 어제 catalog 결과 같은 결로 \"외부 AI에 다시 답해달라\"는 안내가 한 결 더 구체적으로.

## 해야 할 일

- catalog import도 같은 결의 폴백이 박혀있는지 확인. 어제 사용자가 부딪힌 catalog ask_questions 결은 파서가 아니라 스키마 검증이라 결이 다를 자리. 다만 비슷한 결의 관대함이 필요하면 별도 amendment ADR 자리
- 외부 AI 응답의 다른 깨짐 결(코드 펜스 종류 다양화, 헤딩 한국어 변형 등)도 신호 보이면 같은 결로 풀음

## 추천

- 이번 PR(파서 폴백)을 머지하면 사용자가 어떤 결로 응답을 받아도 마크다운 wrapping 없이 바로 import 가능. 외부 사용자 결의 진입 마찰이 한 결 더 줄어듦
- amendment ADR로 정식화할지 검토. 다만 ADR이 정한 결이 아닌 \"파서 관대함\"의 결이라 워크로그 결로 충분할 자리

## 알아둘 것

- `tryParseRawYaml`은 yaml.load의 결을 try/catch로 흡수한다. 잘못된 YAML이 들어와도 throw 안 함. 안전한 결
- raw YAML 결로 폴백한 응답도 `hasStructuredSection: true`로 박힌다. 호출자(applyForgeReview 등)는 changes 배열만 보니 결이 정합
- 사용자가 원본 .yml 파일을 그대로 줄 수 있게 됨. 마크다운 wrapping 결을 박는 안내가 어제까지는 필요했지만 이번 결로 사라짐
- 폴백 에러 메시지가 한 줄 길어졌다. 다음 사용자가 같은 결로 부딪히면 메시지 결에서 어떻게 풀지 안내 받음

## 네 번째 세션의 목표

PR #8(raw YAML 폴백)을 머지한 뒤 사용자가 다시 돌렸는데 forge import-review에서 YAML 자체가 깨진 결을 받았다. 외부 AI가 `reason:` 값에 따옴표 없이 `(예: POST /b-logins/logout)`을 박아 콜론이 새 키로 본 결. 폴백이 silent 실패라 사용자에게 어디가 깨졌는지 안 알려줌.

파서 결의 친절함 결로 풀음. YAML 파싱 실패 결을 yamlError 필드로 호출자에게 노출. logGracefulDegrade가 js-yaml의 라인/컬럼 결과 컨텍스트 결을 그대로 보여주게 박음.

## 배운 점

PR #8의 폴백 결이 silent 실패 결로 박혀있던 자리. yaml 파싱이 깨지면 catch로 흡수해 null 반환했는데, 사용자에게는 일반 에러 메시지로 끝났다. 외부 AI가 만든 결의 어디가 깨졌는지 사용자가 알 결이 없었음.

이번 결로 yaml 파싱 실패 결을 호출자에게 노출했다. js-yaml의 에러 메시지가 라인/컬럼/소스 컨텍스트 결을 이미 잘 박아둬 그대로 보여주는 결이 자연스러웠다. 사용자가 line 77을 보고 콜론 결을 따옴표로 감싸면 바로 풀음.

`reason:` 같은 값에 콜론이 있어 깨지는 결이 외부 AI 응답의 가장 자주 일어날 자리. 다음 사용자도 같은 결로 부딪히면 라인 결과 함께 "콜론이나 # 있으면 큰따옴표로" 안내가 박혀 풀음 결이 한 결 가벼움.

PR #8과 보완 관계. PR #8이 마크다운 wrapping 없는 결을 받아줬고, 이번 PR이 YAML 자체가 깨진 결의 결을 안내. 외부 AI 응답의 자주 깨질 결 둘을 모두 잡았다.

## 해야 할 일

- 6개 검토 프롬프트에 "값에 콜론, #, [, { 결이 있으면 큰따옴표로 감싸세요" 한 줄 강조를 박는 결도 검토. 외부 AI가 처음부터 결을 안 깨도록. 다만 이번 PR로 깨졌을 때 풀음 결이 가벼워졌으니 시급하지 않음
- catalog import에도 비슷한 YAML 깨짐 결 안내가 박혀있는지 확인. 어제 사용자가 부딪힌 catalog의 ask_questions 결과 결이 다름(스키마 검증). 다만 catalog YAML 자체가 깨지는 결의 안내는 별도 결

- 외부 AI 응답 결의 자주 깨질 결을 모은 결을 docs/specs/ 에 짧게 정리할 자리. 미래 기여자가 같은 결을 박을 때 참고. 차후

## 알아둘 것

- yamlError 결은 js-yaml의 결을 그대로 통과. 라인 결과 컨텍스트 결이 한 결로 박혀있어 사용자가 어디를 고칠지 안다
- logGracefulDegrade가 yamlError를 들여쓰기 결로 풀어 출력. parseError와 yamlError가 결이 명확히 갈림
- 결과 객체에 `yamlError` 필드 추가는 기존 호출자(forge/temper/inspect import 결)에 영향 없음. parseError와 hasStructuredSection 결만 보던 결이 그대로 동작
- 사용자가 `.bak` 파일로 결을 다시 시험할 수 있게 결을 둠. 깨진 결의 결을 보여주려고
