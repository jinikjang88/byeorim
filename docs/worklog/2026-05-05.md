## 배운 점

picker 시그니처를 바꾸면서 기존 헬퍼 테스트들이 깨졌다. `pickBlocks(catalog)` 단일 인자에서 `pickBlocks({ catalog, recommendation })` 객체 인자로. 의존성 주입 패턴을 쓸 때 인자 모양을 처음부터 객체로 두면 미래 확장 시 호환성이 살아남는다. 이 자리에서 한 번 학습.

claude 어댑터의 recommendBlocks는 catalog 전체를 보내지 않고 blocks의 일부 필드(id, name, user_desc, priority)만 잘라 보낸다. catalog가 큰 경우 토큰 비용이 빠르게 늘 수 있어서 어댑터 단계에서 자르는 결이 안전. 결정 1(adapter에 새 메서드)을 채택한 다른 이유 자리이기도 하다 — 어댑터가 입력을 자기 입맛에 맞게 정리할 자리를 가짐.

confirmSelection을 'redo'/'proceed' 두 갈래로 한 결이 흐름을 단순하게 유지했다. 셋(예/아니오/자세히)으로 가면 "자세히"가 무엇을 의미하는지 사용자가 헷갈리고, 차단 없이 보여주기만 하면 사용자가 안 읽고 넘어간다. 두 갈래 select가 동행 톤(읽고 결정)과 흐름 가벼움 사이의 균형점.

intent.yml schema_version 1 폴백 자리가 후속 하위 호환의 좋은 예. ADR 0026이 1→2를 박았을 때 마이그레이션 안 둔다 결정했지만, 실제로는 옛 파일을 만나면 빈 user_answers로 폴백해 추천이 빈 배열로 나오게 graceful degradation. 사용자에게 안내 한 줄("AI 추천 없이 진행")로 알린다.

## 아직 열려있는 것

- claude 어댑터의 recommendBlocks를 실제 사용자 도메인으로 manual review 자리. 카페 사장님 1~2명에게 추천이 의미 있는지 확인 필요
- recommendBlocks가 추천 점수(0~1)를 노출해 강한 추천과 약한 추천을 구분하는 자리. 후속 ADR

- prospect 끝에서 smelt 인터랙티브로 자동 이어지는 자리(예: `--continue` 플래그). 지금은 사용자가 두 명령을 따로 친다

block-review-prompt.md에 카탈로그 전체를 담기로 한 결정(ADR 0030 결정 4)이 비개발자 정신과 정합. 외부 AI가 "다른 블럭 X도 같이 보세요" 같은 자리를 짚어주려면 카탈로그 다른 자리도 봐야 한다. prompt가 길어지는 비용보다 검토 가치가 크다.

picker는 user 시점만 보여주고 dev 시점은 prompt 부산물에만 노출하는 결이 두 시점의 책임을 명확히 갈랐다. picker는 "고를 자리"이고 prompt는 "검토 자리". 시점도 자리에 맞게 정렬됨.

# Worklog 이어쓰기 — 2026-05-05 picker 그룹화와 의존성 상세 검토

## 이번 단계의 목표

smelt UX의 세 자리를 한 결로 묶어 벼린다.
1. picker가 카탈로그의 worlds → bundles → blocks 두 단계 그룹을 시각으로 보여줌
2. focused 자리의 description에 priority/effort_days/concerns를 더해 사용자가 블럭 무게를 가늠
3. confirm 단계의 자동 추가/영향/준비물을 catalog lookup으로 한국어 풀이

ADR 0031 한 결로 묶음. 산출물 형식(ADR 0010)은 그대로.

## 변경 사항

### 새 파일
- docs/decisions/0031-smelt-picker-world-grouping-and-dependency-detail.md — 결정 4개(그룹 두 단계, focused description 풍부화, confirm catalog lookup, ADR 0010 호환)
- packages/cli/src/smelt-picker-helpers.js — 순수 함수 4개. buildBlockHierarchy(catalog), lookupBlockDetail(catalog, id), buildBlockDescription(block), truncateOneLine(text, max). 데이터 무관, 도메인 ID 가정 없음
- tests/unit/cli-smelt-picker-helpers.test.js — 헬퍼 단위 테스트 16개

### 손댄 파일
- packages/cli/src/smelt.js — Separator import, defaultPickBlocks가 hierarchy로 두 단계 그룹화 + buildBlockDescription으로 focused description 합성, defaultConfirmSelection이 catalog 인자 받아 lookupBlockDetail로 한국어 풀이, interactiveSmelt가 confirmSelection에 catalog 전달
- tests/unit/cli-smelt.test.js — picker가 worlds/bundles 받음, confirmSelection이 catalog 받음, autoAdded ID로 lookup 가능 3개 추가
- README.md — 제련 절에 picker 그룹화/focused description/confirm 한국어 풀이 한 단락

### 검증 결과
- npm test 346개 모두 통과(이전 327 + PG 신규 19: 헬퍼 16, smelt 3)
- ESLint, Prettier 통과

## 배운 점

catalog의 hierarchy(worlds → bundles → blocks)가 catalog.schema.json에 잘 박혀있어서 헬퍼 함수가 자연스러웠다. 데이터 구조가 명확하면 UX 변경이 데이터 가정 없이도 흐른다(섹션 8 데이터 무관성 정신).

@inquirer/prompts의 Separator로 두 단계 그룹화가 깨끗하게 됨. 한 단계 깊이는 `─── 세계 ───`, 두 단계는 `  · 번들`로 시각 차이를 두어 한눈에 구조가 보인다.

confirmSelection이 catalog를 받게 시그니처를 늘릴 때 기존 mock 테스트가 안 깨졌다. 객체 인자라 새 키를 무시하고 통과. 객체 인자 패턴이 미래 확장에 강한 자리(이전 BR 작업에서도 같은 결이었음).

defaultConfirmSelection은 한 함수에 출력 자리가 많아져 길어졌다. 출력 한 결을 helper로 빼는 자리도 있지만 이번 출시는 함수 안에 두고 가독성 우선. 후속 자리에서 출력이 더 풍부해지면 helper로 갈라놓을 결.

## 아직 열려있는 것

- claude 추천 manual review 자리는 그대로 열려있음(이전 워크로그). docs/manual-checklist.md를 만드는 자리는 사용자가 일시 중지를 요청해 다음으로 미룸
- picker가 매우 큰 카탈로그(blocks 50+, bundles 20+)에서 첫 화면 길이 부담. 사용자 피드백 받으면 collapsible 그룹 결 검토(후속 ADR)
- focused description이 두세 줄 단락이라 짧은 화면(80자 좁은 터미널)에서 잘릴 가능성. 사용자 피드백 받으면 truncation 자리 검토
- confirm 표가 자동 추가 6개+ 자리에서 한 화면 안 들어올 수 있음. 후속 자리(예: pagination 또는 한 줄 요약 + "자세히 보기")

## 배운 점

ADR 0012의 표준 옵션 식별자가 표준이라 LLM이 그 외의 값을 돌려줄 위험이 있다. 어댑터 본체에 ARCH_VALID_VALUES 안전망을 박아 두 자리에서 검증한다(system 프롬프트 + 어댑터 코드). cli의 shape.js가 한 번 더 ensureChoicesValid로 거른다. 세 자리 검증이 중복처럼 보이지만 LLM의 비결정성 앞에서는 안전망이 겹쳐 있어야 한다. system 프롬프트가 어겨도 어댑터가 거르고, 어댑터가 어겨도 cli가 거른다.

interactiveShape 시그니처를 객체 인자({context, recommendation})로 바꾸면서 기존 9개 테스트의 askArchitecture 호출 자리가 모두 바뀌었다. smelt에서 picker 시그니처를 객체로 바꾼 결(2026-05-05 워크로그 첫 묶음)을 그대로 따라간 결과. 객체 인자 패턴은 기존 호출자(테스트의 `async () => FIXED_CHOICES`)가 그대로 살아남고, 새 인자가 추가돼도 기존 자리가 안 깨지는 점이 매번 좋다. 이번에 깨진 두 테스트는 명시적으로 인자를 destructuring한 자리뿐이다.

confirmArchitecture를 추가하면서 기존 테스트 4개(정상 흐름, context 전달, cascade 답안, state 갱신)가 모두 새 의존성을 주입해야 했다. ALWAYS_PROCEED 헬퍼 한 줄로 해결됐지만, 의존성 주입이 늘어날 때마다 기존 테스트의 setUp이 무거워진다. 이번 출시는 그 정도가 적당하지만 의존성이 5개 넘어가면 테스트 헬퍼(`setupShapeTest`)로 빼는 결도 검토할 자리.

interactiveShape를 setup 헬퍼로 쓰는 다른 테스트(cli-forge, cli-set 외 9개 파일) 14개 자리도 한번에 갱신해야 했다. confirmArchitecture를 안 주입하면 defaultConfirmArchitecture가 stdin select로 빠지면서 테스트가 무한 대기로 멈춘다. 첫 테스트 실행에서 그 자리가 보이지 않다가 npm test 전체가 30분 넘게 멈춰서야 발견됐다. interactiveSmelt가 같은 결을 가진 자리에서 이미 학습한 패턴이지만 shape에 옮길 때 다른 테스트의 setup도 함께 봐야 한다는 점이 다시 학습됐다. 같은 결을 다른 자리에 옮길 때 setup 호출자도 한 결로 봐야 한다.

claude 어댑터의 system 프롬프트에 ADR 0012의 옵션 표를 박은 결정(prompt caching 적중)이 일관성 자리에서도 좋다. 매번 같은 system 메시지가 가서 LLM이 옵션을 잘못 추측할 자리가 줄어든다. 사용자 메시지로 옵션을 매번 보내는 자리가 토큰은 비슷해도 캐시 적중에서 손해.

## 배운 점

picker description의 우선순위 결(추천 user reason → 옵션 tradeoff → 빈 자리)을 buildOptionDescription 한 함수에 모았다. 이렇게 모으니 단위 테스트 3개로 우선순위 자리가 한 자리에서 검증된다. shape.js의 buildOptionsForKey는 헬퍼를 부르기만 하니 흐름이 단순. 우선순위 결정은 헬퍼가, 옵션 합성은 호출자가 책임지는 분리.

옵션 tradeoff를 ARCHITECTURE_CHOICES와 같은 자리에 둔 결이 미래 변경에 강하다. 옵션 추가/변경 시 한 자리에서 value/name/tradeoff 셋을 함께 본다. 별도 ARCHITECTURE_TRADEOFFS 표를 두면 두 자리 동기화 부담이 생기지만 같은 객체 안에 두면 그 부담이 없다.

defaultAskArchitecture가 log 인자를 받게 시그니처를 늘릴 때 기존 호출자(테스트의 `async () => FIXED_CHOICES`)는 그대로 통과했다. 객체 인자 패턴이라 새 키를 무시한다. 작업 A에서 학습한 같은 결이 작업 C에서도 살아남았다(2026-05-05 첫 묶음 워크로그).

formatContextSummary와 formatChoicesSummary를 헬퍼로 빼니 단위 테스트가 select prompt 자리(stdin 막힘)와 분리된다. 마크다운 본문/터미널 출력의 결을 헬퍼가 검증하고, 통합 테스트는 헬퍼가 호출되는 자리만 본다. 작업 B의 shape-prompt 분리와 같은 정신.

confirm 출력 본문이 길어졌지만 한 화면 안에 들어온다(4개 결정 × 2줄 = 8줄 안팎). 더 풍부해지면 한 화면을 넘을 수 있는데 그 자리는 후속.

## 아직 열려있는 것

- picker description은 옵션 한 줄만 나온다. 트레이드오프 두세 줄로 풀어쓰는 자리는 후속(긴 description은 inquirer가 다 보여주지 못할 수 있어 검증 필요)
- 부분 재선택(예: 언어만 다시 고르기)은 작업 A의 redo 루프 그대로(전체 4개 다시). 후속 ADR 자리
- claude 추천 reason과 옵션 tradeoff가 충돌할 때(예: 추천이 reason 없이 비어있는 자리) tradeoff가 fallback으로 박히는 결. 사용자에게 두 결을 어떻게 보여줄지 manual review 자리
- 외부 검토 부산물(architecture-review-prompt.md)에 옵션 tradeoff를 함께 보낼지. 이번에는 안 넣었지만 외부 AI가 트레이드오프 결을 자기 시각으로 답하도록 두는 결과 정합. 사용자 피드백 받으면 검토

## 배운 점

forge는 비인터랙티브 변환 단계라 "사용자 선택 자리가 없다"고 생각했지만, 검토 자리는 별개라는 점을 배웠다. 선택은 없어도 결과를 보여주고 "이대로 가실래요?" 묻는 자리는 의미가 있다. shape의 confirm-only 패턴이 forge에도 그대로 옮겨지는 결.

`runForge`를 그대로 두고 `interactiveForge`를 새로 둔 결이 ADR 0023의 옵셔널 어댑터 결과 짝을 이룬다. 비대화 호출(테스트, 자동화)은 후행 호환을 가지고, 사용자 흐름은 인터랙티브로 풍부해진다. 두 함수가 공유하는 build 로직을 buildContracts/buildContractsDoc 작은 자리로 분해하니 두 자리에서 같은 결이 살아남는다.

mock 어댑터의 redo 헛흐름을 인지하는 안내 한 줄(`어댑터가 결정적이라 다시 만들어도 같은 schema가 채워질 거예요`)을 둔 결이 사용자 신뢰에 맞다. redo 자체를 막으면 흐름이 일관성을 잃고, 안 알리면 사용자가 헛흐름을 헤맨다. 어댑터의 결정성을 picker가 알 자리(adapter.name 화이트리스트)는 임시 결. 어댑터 인터페이스에 `isDeterministic` 플래그를 박는 자리는 후속 ADR.

검토 화면 표시 깊이를 "블럭별 한 줄 + 메서드/path 줄"로 박은 결이 한 화면 안에 들어온다(블럭 5~10개라면 30~50줄). schema 자체(필드명, 타입)까지 풀어 보여주면 한 화면을 넘는다. schema 검토는 외부 검토 프롬프트(후속 ADR) 자리로 미루는 결이 정보 과다 자리를 막아준다.

interactiveForge의 의존성 주입(`confirmContracts`)이 select prompt 자리(stdin 막힘)와 단위 테스트를 분리한다. shape/smelt와 같은 결. 새 인자가 미래에 늘어도 객체 인자 패턴이라 기존 호출자가 그대로 통과하는 자리는 두 단계에서 검증됨.
