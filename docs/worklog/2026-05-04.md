## 배운 점

처음 reality-check-questions.js를 cli 패키지에 두려고 했는데 mock 어댑터(ai 패키지)도 같은 시드를 써야 한다는 자리에서 의존성 역행이 보였다. core로 옮기니 cli와 ai 양쪽이 같은 진실의 자리(섹션 8 패턴 일관성)를 본다. core의 정의를 "순수 함수"에서 "순수 함수와 데이터"로 한 단어 넓히면서 패키지 머리 주석도 갱신.

`buildIntent`가 reality_check_status를 인자로 받게 시그니처를 바꿨다. 이전에는 항상 'pending'으로 박혀있었는데 RC 호출 결과에 따라 'completed' 또는 'skipped'로 갈리는 자리. 함수 인자 하나 늘어난 비용 vs 호출 후 dict 변경의 모호함 사이에서 인자 추가 길을 골랐다(불변 리턴 결).

ADR 0003 결정 3의 강한 신호 자리는 이번 출시에서 prospect 단계가 아니므로 사용하지 않고 `legal_warnings` 자리에 모아두기만 했다. Inspect 단계가 같은 데이터를 그대로 받아 다시 보는 자리를 미리 열어둠. 후속 ADR에서 그 결을 마무리한다.

mock의 generateRealityCheck는 시드를 그대로 통과시킨다. observation을 빈 문자열로 두는 결이 도메인에 대한 거짓 일반론을 만들지 않는 자리(ADR 0026의 "빈 자리는 빈 자리로" 정신을 RC에 옮김).

## 배운 점

처음 importCatalog를 sync 함수로 짰는데 테스트에서 `assert.rejects`를 썼더니 4개가 깨졌다. sync throw는 `assert.throws`로 받아야 한다. 함수가 sync인지 async인지가 테스트 API 선택을 바꾼다. 같은 결의 함수들이 한 자리에 묶여있도록 시그니처 일관성을 신경 써야 함.

prospect-prompt.js의 SYSTEM_TEXT가 packages/ai/src/claude.js의 CATALOG_SYSTEM_PROMPT와 비슷하지만 다르다. API용은 structured output schema가 형식을 강제하므로 본문이 짧고, 외부 AI용은 자연어로 YAML 형식과 예시를 안내해야 하므로 본문이 풍부하다. 두 자리가 한 결을 따르되 텍스트는 분리하는 게 옳다(API는 짧게, 외부는 자세하게).

prompts/ 디렉토리를 .beoreum/project/ 아래에 새로 두면서 .beoreum/ 레이아웃이 한 결 더 풍부해졌다. catalog-prompt.md 한 파일만 있어 가벼움. 미래에 다른 자리(예: smelt 단계의 외부 프롬프트)도 같은 디렉토리에 모일 수 있다.

ADR 0006의 7단계 메타포를 깨뜨리지 않으면서 보조 명령(`prospect import-catalog`)을 추가했다. 7단계는 그대로 살아있고 보조 명령은 prospect 명령 안에 서브명령으로 자리잡음. 메타포 일관성과 기능 확장의 균형.

## 아직 열려있는 것

- import 후 RC 자동 갱신 자리는 후속 명령(`beoreum prospect refresh-rc` 같은) 자리. 이번 출시는 사용자에게 안내까지만
- 외부 AI 응답을 stdin으로 받는 결(파이프 사용)은 후속 자리. 지금은 파일 경로만 받음
- catalog-prompt.md 본문에 catalog.schema.json 부분집합 예시를 직접 인라인했다. 명세 변경 시 prompt 텍스트도 동기화해야 함. 한 자리에서 진실로 두려면 schema에서 예시를 자동 합성하는 결로 발전 가능
- 사용자가 검증 실패 → 외부 AI 다시 → 검증 통과 사이클을 몇 번 돌아야 할 수 있다. 검증 오류를 사용자가 외부 AI에 그대로 보여줄 수 있게 메시지를 잘 다듬어둠
