## 배운 점

5개 import 모듈이 거의 같은 결을 박고 있던 게 이번에 분명히 보였다. parseReviewResponse → validation 루프 → picker 루프 → yml 갱신 → summary 출력. 이 다섯 단계가 200~300줄로 5번 반복되고 있었다. helper 6개로 추출하니 각 모듈이 60~120줄로 줄어 의도 자리(validate/locate/applyChange)만 남는다. 코드 양 줄어드는 결보다, 다음 변경 자리(예: picker 메시지 한국어 다듬기)에 한 곳만 손대면 5곳이 따라가는 결이 큰 이득.

함수 인자로 차이 주입한 결이 자연스러웠다. 클래스 상속 결을 안 가져온 게 ESM 결과 정합. validate(item) → locate(item) → describe(item) → applyOne(item, ctx) 네 함수만 모듈이 박고 helper가 그 위에서 흐름을 안다. 시니어 개발자가 한 모듈을 익히면 다른 모듈도 즉시 안다.

inspect-import의 부분 통합 결이 흥미로웠다. confirmFinding은 외부에서 inject되는 인자라 시그니처를 바꾸면 사용자 코드가 깨진다. helper는 `{ change, located }` 결로 호출하지만 inspect는 `{ finding }` 결을 외부에 약속했다. 둘 사이에 wrappedConfirmChange 한 줄을 박으니 외부 API는 보존하면서 helper 사용 가능. 미래에 다른 모듈도 같은 결로 통합 가능.

smelt와 shape의 defaultConfirmChange 시그니처가 forge/temper와 달랐던 게(`{ change, block }` vs `{ change, oldValue }` vs `{ change, located }`) 이번에 통일되는 결이 좋았다. 5개 모듈이 같은 helper signature(`{ change, located, index, total, log }`)를 따라가니 미래 새 모듈 추가 시 패턴이 분명. located는 locate가 반환한 객체 통째로 — 호출자가 located.X 결로 풀어쓴다.

ESM의 import 안 쓰는 결에 한 번 걸렸다. shape-import.js에서 readFileSync를 import에서 빼버렸는데 loadYaml 내부에서 쓰고 있어 다시 추가. ESM의 import는 사용처를 다 추적해야 하는 결이라 자동 정리 도구가 없으면 빠뜨림. 미래에 unused import 검출 lint 결을 박는 결도 자연스러움.

inspect의 picker가 적용된 finding을 직접 accepted 배열에 모으는 결이 다른 4 모듈과 다르다. 다른 모듈은 applyChange가 contracts/scenarios/architecture를 mutate하는데 inspect는 yml의 external 섹션 통째로 교체라 accepted 배열을 따로 모으는 결. 두 패턴이 helper 안에서 같은 결로 동작하니 helper의 결이 충분히 일반적.

CODE_OF_CONDUCT.md 작성에서 Contributor Covenant 2.1 한국어판을 그대로 붙이지 않은 결이 자연스러웠다. 표준판은 번역체가 강해 벼림의 다른 문서(README, MANIFESTO, CLAUDE.md)와 결이 안 맞는다. 표준판의 4단계 시행 가이드라인 골격은 그대로 가져오되 문장은 단정형으로 다시 썼다. 공식 표준에서 가져왔다는 출처는 마지막에 명시.

## 변경 사항

### 새 파일

## 배운 점

이름 변경 같은 결은 sed 일괄 치환과 git mv로 빠르게 처리할 수 있지만, 결정 기록(이 ADR 0055) 자체는 "벼름"을 보존해야 의미가 산다. find의 `-not -path` 결로 ADR 0055를 sed 대상에서 빼낸 자리가 깔끔했다. 이 결을 미래에도 따라가면(예: 큰 이름 변경 마이그레이션) ADR이 결정 시점의 단어를 그대로 담는다.

`.prettierignore`처럼 확장자 없는 파일이 sed find 패턴에서 빠지는 자리가 한 번 깨졌다. 보정으로 grep -rIl로 텍스트 파일 전체를 다시 훑어 누락 없이 처리. 미래에 비슷한 일괄 치환 결을 박을 때는 처음부터 `find -type f` + `grep -rIl` 두 결을 모두 써서 누락을 막는 결.

`.idea/`가 `.gitignore`에 있어 git이 추적하지 않는다. 그래서 `.idea/beoreum.iml`을 git mv하려 하면 fatal로 멈춘다. 이런 자리는 그냥 mv로 처리하고, modules.xml 안의 모듈 경로 참조도 같이 갱신해야 IntelliJ가 다시 열 때 모듈을 인식. workspace.xml의 GitHub URL은 IntelliJ가 다음 실행 시 .git/config 기반으로 자동 갱신하니 그대로 둠.

이전 세션의 워크로그(2026-05-08 세 번째 세션)에서 "다음 ADR은 0055로 CI 게이트"라고 예약된 자리가 있었는데, 이번 결정이 더 시급해 0055를 가져갔다. CI 게이트 ADR은 다음에 박을 때 0056으로. 워크로그의 ADR 번호 예약은 결정적이지 않다는 결을 한 번 더 새김.

## 해야 할 일

- 외부 작업: GitHub repo 이름을 `beoreum`에서 `byeorim`으로 옮김. `git remote set-url origin <new-url>`도 함께. 이건 사용자가 GitHub UI와 셸에서 직접 처리하는 자리

- IntelliJ를 다음에 열 때 workspace.xml의 GitHub URL이 자동 갱신되는지 확인. 안 되면 수동 갱신
- 다음 ADR 번호는 0056으로(이전 세션의 "ADR 0055 = CI 게이트" 예약은 무효)

## 배운 점

영문판을 만들 때 한국어 결을 단어 단위로 옮기지 않고 "같은 약속을 영어 사용자에게 자연스러운 결로 다시 쓴다"는 결로 가니 자연스러웠다. 예를 들어 한국어판의 "결", "자리" 같은 단어는 영어로 그대로 옮길 결이 없으니 "track", "approach", "place" 같이 문맥에 맞는 단어를 골랐다. CLAUDE.md 섹션 10의 글쓰기 원칙은 한국어 글에 한정되지만, 영문판도 같은 정신(과장 형용사 금지, 마케팅 카피 결 금지, 구체 명사/동사)을 따라가니 두 판본의 톤이 맞물림.

"두 문서가 어긋나면 한국어판이 정본"이라는 결을 각 영문판 상단에 박은 결이 깔끔했다. 일관성을 보장하는 약속이면서, 향후 정식 한/영 정책(ADR 0056)을 박을 자리를 비워둔다. 정책이 없는 상태에서 영문판이 외부에 노출되면 "어느 쪽이 정본인지" 묻는 사람이 생기는데 한 줄로 답이 박혀 있으니 운영 부담 작음.

LICENSE를 그대로 둔 결이 자연스러웠다. MIT 라이선스는 영문 원문 자체가 표준이라 한/영 두 판본을 만들면 오히려 라이선스 해석이 흔들린다. README의 "기여와 라이선스" 섹션도 LICENSE에는 별도 (English) 링크를 박지 않았다.

IDE 진단이 새로 만든 파일을 즉시 인덱싱 못 하는 결을 한 번 더 확인했다. 파일을 만들고 같은 메시지에서 link로 참조하면 IDE는 잠깐 ⚠를 띄운다. ls로 파일 존재를 확인하면 끝. 다음 IDE 새로고침 때 사라짐.

## 배운 점

영문 README를 한국어판과 1:1로 옮기지 않는 결이 자연스러웠다. 한국어판은 비기술 창업자에게 친절하게 풀어쓴 결이 강해(예: "안전망", "출시 직전 점검") 200줄을 차지하지만, 영문판의 1차 사용자는 GitHub에서 처음 들어오는 영어 사용자다. 그들에게는 사명, 7단계, 빠른 시작 셋이 핵심. 자세한 결은 한국어판 또는 ADR로 보내는 결이 맞다. README.en.md가 한국어판의 50% 분량으로 끝났다.

영문 README에서 7단계 표의 한국어 단계명("탐광", "제련")을 괄호 결로 함께 표기한 결이 좋았다. `byeorim prospect` 명령은 영어인데 단계 메타포 자체는 한국어가 정본이라 영문판이 한국어를 보존하는 결이 자연스럽다. 외부 사용자가 한국어 ADR이나 워크로그를 마주칠 때 단계명을 알아볼 진입점이 됨.

영문 README에서 "Promises" 섹션의 톤이 한국어판의 "약속"과 결이 맞물렸다. 한국어판은 "유료 등급, 게이트 기능, 옵트인 없는 사용 정보 수집은 없다"는 결인데, 영문판에서 "No paid tiers, no gated features, no opt-out telemetry"로 옮기니 같은 약속이 같은 단정형으로 박힌다. CLAUDE.md 섹션 10이 한국어 한정이지만 정신(과장 형용사 금지, 마케팅 카피 금지)은 영문판에도 그대로 작동.

LICENSE 섹션의 결정이 깔끔했다. LICENSE는 MIT 표준 영문이라 영문 README에서도 별도 (Korean) 링크 없음. CONTRIBUTING/CoC/Security만 (Korean) 링크를 단다. 한국어 README의 결과 미러.

## 변경 사항

### 새 파일

- docs/decisions/0056-bilingual-docs-policy.md — 한/영 듀얼 문서 정책. 세 가지 결정(정본=한국어, sync 책임=같은 PR, 영문판 의무 범위=외부 진입점만)

### 손댄 파일

- CLAUDE.md 섹션 9 — 완료 정의 체크리스트에 "외부 진입점 문서를 수정했다면 한/영 두 판본을 같은 PR에서 갱신했다 (ADR 0056). 한국어판이 정본" 한 줄 추가

### 검증 결과

- prettier 통과(CLAUDE.md, ADR 0056)
- 코드 변경 없음. 테스트/린트 영향 없음

## 배운 점

ADR을 박은 뒤 CLAUDE.md 섹션 9에 한 줄 박는 결이 "정책 종이"와 "실제 작업 게이트" 사이를 잇는 결이었다. ADR만 만들고 끝내면 미래 기여자가 ADR을 안 읽으면 정책이 무력화된다. CLAUDE.md 섹션 9는 매 작업의 완료 체크리스트라 PR 머지마다 강제로 마주친다. 한 줄 추가가 ADR을 살린다. 미래에 다른 ADR도 머지 게이트로 만들고 싶다면 같은 결로 섹션 9에 박는다.

ADR 0056의 결정 3(영문판 의무 범위)을 "외부 진입점만"으로 좁힌 결이 자연스러웠다. 워크로그/일반 ADR/도메인 주석까지 모두 영문화하면 1인 메인테이너 결로 비현실적이다. 외부 사람이 첫 진입에서 막히지 않으면 충분하고, 글로벌 관심 신호가 보일 때 점진 확장하는 결이 운영 부담과 글쓰기 결을 함께 보호한다.

ADR의 sync 책임 결정(같은 PR에서 함께 갱신)이 외부 영문 기여자에게 진입 장벽이 될 수 있다. 다만 ADR에 "외부 영문 기여자가 한국어를 못 짤 결이면 PR 본문에 '한국어 갱신 필요' 표시. 메인테이너가 결을 채워 넣음"이라는 결로 보완책을 박았다. 이 안내는 CONTRIBUTING.en.md 차후 갱신에 박을 자리.

자동 번역 결을 옵션 C로 검토한 뒤 "차후 검토할 자리"로 미룬 결이 깔끔했다. 기계 번역은 글쓰기 원칙(섹션 10) 정신과 결이 안 맞는다. 1.0 출시 시점에 영문판 범위가 더 넓어지면 자동 번역 결을 다시 본다. 그때 별도 ADR.

- 1단계 결과물 모두 커밋. 일곱 세션 누적된 변경(README/CONTRIBUTING/CoC/Security 한/영 + ADR 0056 + CLAUDE.md 섹션 9 + 워크로그)을 묶음 또는 분할 커밋
- 공개 가시성 켜기는 GitHub UI에서 사용자가 직접
- "good first issue" 라벨 셋업은 공개 직후 1주일 안에. CONTRIBUTING이 약속한 라벨

## 추천

- 커밋 결: 1단계 마무리 결을 한 커밋으로 묶는 결이 자연스럽다. 한/영 4종 + ADR 0056 + CLAUDE.md + 워크로그가 같은 약속을 박는 작업이라 묶음으로 보는 결이 미래 기여자에게 분명. 분할하면 ADR과 영문판이 분리되어 결이 흐려짐

## 알아둘 것

- ADR 0056의 옵션 C(자동 번역)는 1.0 시점에 다시 볼 자리. 지금은 사람 손 결
