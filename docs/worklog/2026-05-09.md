## 배운 점

추상 스펙(형식만)과 구체 예시(샘플 포함)의 차이가 외부 AI 결을 결정한다. shape/forge/temper/inspect의 형식 스펙은 이미 자세히 박혀 있었는데 사용자가 결이 안 맞는다고 했다. 이는 AI가 abstract spec을 읽어도 응답 결을 만들 때 자유 형식 부분과 형식 섹션의 관계, 헤딩 결, yaml 코드 펜스 결을 다르게 박기 때문. 짧은 예시 한 덩이가 "자유 형식 → 형식 섹션 → yaml" 순서를 한눈에 보여줘 결을 강제한다.

샘플을 자유 형식 3-4 헤딩 + 형식 섹션 1-2 변경으로 짧게 잡은 결이 자연스러웠다. 너무 길면 AI가 길이를 따라가 답이 짧아지고, 너무 짧으면 결이 안 보인다. shape는 1 변경, forge는 2 변경, temper는 1 변경, inspect는 2 findings로 균형.

샘플 안에 도메인 무관 placeholder(`<블럭_id>`, `<resource>`)를 박은 결이 CLAUDE.md 섹션 8(데이터 무관성)과 정합. commerce 결을 박지 않아 사용자 도메인이 reservation/healthcare 어디든 결이 맞는 자리가 살아남.

shape의 샘플에서 java + h2 + 한 덩어리 → sqlite 옮기는 결을 박은 게 흥미로웠다. 표준 옵션 표 안의 결만 사용하는 결을 명시적으로 보여줌으로써 외부 AI가 카탈로그 외 값을 추천하지 않게 결을 잡는다.

테스트 결로는 "예시 응답" 키워드와 자유 형식 헤딩 + 형식 섹션이 한 결로 들어있는지 정규식 한 줄로 검증. 미래에 샘플 결이 갱신되어도 키워드 결이 살아있는지를 보장한다. 샘플 본문을 정확히 매칭하지 않아 다듬을 자리가 자유.

## 알아둘 것

- 샘플은 README에 박힌 결이 아니라 외부 AI에 보내는 프롬프트 안 결이라 비기술 사용자가 직접 보지 않는다. 다만 import-review로 다시 들어올 때 사용자 응답 결로는 영향이 큼
- 샘플에서 `<블럭_id>`, `<resource>` 같은 placeholder를 박았는데, 외부 AI가 이걸 그대로 placeholder로 답할 수 있다. 다만 import-review는 placeholder 결을 거부하지 않고 사용자가 picker에서 적용/건너뛰기로 결정. 샘플 결이 외부 AI에게 "구체값 결을 채워달라"는 안내가 부족할 수 있음. 미래 amendment 자리
- temper-prompt에 단위 테스트 파일이 없는 결을 그대로 둠. 통합 테스트가 비슷한 결을 봐주고 있어 작은 결의 변경(샘플 한 덩이 추가)에 대해서는 충분. 차후 temper 단위 테스트를 박는 결도 자연스러움
