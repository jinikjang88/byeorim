# Worklog — 2026-04-28 (후속 세션, 세움 단계 추가)

## 이번 세션의 목표
forge-protocol v0.5.0의 emit과 verify 두 단계를 벼림의 비춤이 흡수할지 별도 단계로 둘지 결정한다. 비춤이 다관점 검수라는 본 책임에서 멀어지지 않도록, 둘을 묶는 한 새 단계를 다듬과 비춤 사이에 들인다. 6단계 메타포는 표준이라 ADR이 필요한 자리(ADR 0002 미래 묶임 조항).

## 변경 사항
- `docs/decisions/0006-add-stage-for-emit-and-verify.md` 신규. 결정 1(별도 단계 한 개), 결정 2(이름 세움/Set), 결정 3(위치 다듬과 비춤 사이) 셋을 한 ADR에 묶었다. 갈음과 마감을 후보에서 뺀 사유도 검토한 옵션에 남겼다

- `CLAUDE.md` 갱신. 섹션 6의 "6단계 메타포"를 "7단계 메타포(ADR 0006)"로, 7번째 단계 추가 예시를 8번째 단계로, 섹션 8 명령어 목록에 set과 별칭 set을 다듬과 비춤 사이로 끼웠다
- `docs/MANIFESTO.md` III장 갱신. 제목 "6단계 메타포"를 "7단계 메타포"로, 본문에 세움 한 단락을 추가했다. 다듬의 정의도 "통과해야 할 의도를 짓는 자리"로 명확해졌고, 통과 여부 확인은 세움이 진다는 분업이 본문에 박혔다. 명령어 행에도 set이 들어갔다

- 회귀 확인을 위해 npm test를 한 번 더 돌렸다. 41/41 통과(이전 세션과 동일)

## 배운 점
- ADR 0002의 결정 1을 본문 자체에서 7단계로 다시 쓰지 않고, 같은 ADR에 후속 메모를 한 줄 단위로 끼우는 형태로 갱신했다. 결정 시점의 사고가 박제되어야 6개월 뒤 기여자가 "왜 6단계였다가 7단계가 됐는지"를 추적할 수 있다. 이 패턴은 다음 ADR 갱신에도 그대로 쓴다
- 이름 후보 세 개(갈음, 마감, 세움) 중 갈음을 빼는 결정적 이유는 다듬과의 한국어 어감 중복이었다. 영문 표면(Hone vs Temper)에서는 다른 단어처럼 보이는데 한국어 표면(다듬 vs 갈음)에서는 같은 일처럼 들린다. 7단계로 확장한 보람이 한국어 사용자에게는 사라질 수 있는 자리다. 한국어 결을 우선해서 결정했다
- 마감을 빼는 이유는 단어 어감의 시간 위치였다. 마감 뒤에 비춤이 한 번 더 있으면 어느 한쪽이 군더더기로 들린다. 단어가 흐름의 시간 위치를 강하게 암시하는 자리에서는 의미보다 어감이 결정적이다
- 세움은 영문 set이 본명과 별칭이 같아 학습 비용이 0이다. 세 글자 별칭 정책 안에서 가장 가벼운 자리

- 7단계 확장에 따른 카탈로그 데이터 영향은 없다. 현재 카탈로그 스키마는 단계 정보를 직접 가지고 있지 않다(블럭은 단계가 아니라 도메인 구조를 표현)

- 의존성 방향을 강제하는 린트 규칙은 여전히 없다

- 의존성 방향 강제 린트 규칙은 여전히 없다

## 배운 점
- async 함수에서 `try { return fn() } finally { rmSync }` 패턴은 finally가 비동기 fn 완료 전에 도는 함정이 있다. `try { return await fn() }`로 await를 끼우면 finally가 비동기 완료 후에 도는 것을 JavaScript 명세가 보장한다. prospect 테스트에 같은 함정이 남아있는데 Windows의 관대한 파일 잠금 처리 덕에 테스트가 우연히 통과하는 자리. 다음 리팩토링 후보
- selected-blocks.yml과 decisions.yml을 분리한 결정이 사용자에게 보이는 결로 살아난다. selected-blocks.yml은 다음 단계의 입력(자동화), decisions.yml은 사용자가 답을 적는 자리(사람의 일). 한 파일에 묶지 않은 게 동행 톤과 정합
- ADR 0010 결정 4(prerequisites 객체 전체 직렬화)가 자기 완결성을 만든다. 카탈로그가 미래에 바뀌어도 smelt 시점의 결정이 보존된다. 역사 요구사항(섹션 5)이 형식에 박혔다
- decisions.yml의 빈 answer 자리는 사용자가 파일을 열었을 때 어디에 답을 적는지 한 줄 안내가 된다. 형식이 곧 사용자 인터페이스라는 작은 사례

## 배운 점
- withTempCwd가 sync인 함수에서 `try { return fn() } finally { rmSync }`는 fn이 비동기일 때 함정을 만든다. JavaScript 명세상 finally는 sync return 직전에 실행되므로, 비동기 fn이 await로 yield하면 finally가 fn 완료 전에 도는 자리가 생긴다. 기존 prospect 테스트가 mkdirSync의 recursive 재생성 덕에 우연히 통과해 빚이 숨어있었다. interactiveProspect는 await 뒤에 runProspect가 state.yml을 다시 읽어 그 함정에 직접 부딪혔고, 빚이 코드 변경의 압력으로 드러났다. async withTempCwd + `return await fn(cwd)`로 finally가 fn 완료 후에 도는 자리를 명세 차원에서 보장하도록 갱신
- ADR 0011의 의존성 주입 패턴이 두 번째 자리(prospect)에서 첫 번째 자리(smelt)와 정확히 같은 결로 들어갔다. 정책이 코드 패턴을 만든다는 작은 증거
- defaultAskInput의 validate 함수가 빈 입력을 한국어로 다시 묻는다. inquirer의 prompt 자체가 사용자 인터페이스의 일부이고 한국어 안내가 그 안에서 살아난다
