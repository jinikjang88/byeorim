## 배운 점

워크로그 8개를 다시 읽어보니 한 단락에 "자리"가 다섯 번 이상 박힌 곳이 여럿 있었다. AI 지문의 새 자국이 됐고, 의미가 모호한 채로 채우는 단어가 됐다. 사용자가 "추천 / 해야 할 일 / 이런 것들이 있다"로 갈라보자는 결을 줘서 셋으로 박았다. 다음 세션을 시작하는 사람이 "해야 할 일"부터 보고, "추천"을 검토하고, "알아둘 것"은 흘려 읽는 결로 분리. 단순한 분리지만 인지 비용이 줄어든다.

ADR 0046이 한 ADR로 6개 결정을 묶었지만 각 결정이 평행해서 한 묶음으로 풀렸다. healthcheck(결정 1)는 표준이라 4 generator가 각자 emit, 두 .env(결정 2)도 4 generator가 각자 idiom대로 만들고, 두 안전망(결정 4)도 4 곳에서 같은 placeholder prefix를 검사. 결정 6의 "각 언어 표준 idiom" 결을 박은 게 의미 있었다. Spring은 application.yml + profile, Node/Python은 .env, Vite는 mode. 각 언어 사용자가 자기 표준을 그대로 본다.

devPlaceholder 헬퍼 한 곳에 prefix 마커가 모여 있어 미래에 마커를 바꾸려면 그 한 곳만 갱신하면 된다. ADR 0046 결정 5의 표준 마커가 코드 한 곳에 박힌 결.

`existsSync`로 .env / .env.production / application.yml을 보호하는 결을 박았다. set이 다시 실행될 때 사용자가 채운 prod 값이 덮이지 않게. 다른 generated 파일(server.js, routes.js)은 항상 덮어쓰는데 env 파일만 customization-aware. 책임 분리: 코드는 generator의 결, env는 사용자의 결.

Java의 .gitignore는 application.yml은 commit 가능(dev placeholder만 박혀있어 안전), application-production.yml만 gitignore. Spring 관례를 따른 결이라 Java 사용자에게 자연스럽다. Node/Python은 .env 둘 다 gitignore(이쪽 idiom). 4 generator가 같은 결을 각 언어 표준으로 풀어낸 결.

vite.config의 prod build 가드는 빌드 타임 검사라 runtime throw 결과 다르다. import.meta.env가 빌드 산출물에 박히기 때문에 빌드 자체에서 막아야 dev placeholder가 prod 번들에 안 들어간다. defineConfig 함수형 API + loadEnv 패턴이 깔끔하게 풀어줬다.

Python의 model_validator(mode="after")가 settings 인스턴스 검증의 자연스러운 결. pydantic v2의 데코레이터가 placeholder prefix 검사를 한 곳에 모은다. ValueError를 raise하면 pydantic이 ValidationError로 감싸 서버 시작 실패가 분명한 결로 사용자에게 도달.

ADR 0044의 singleton 결과 ADR 0046이 평행하게 살아남았다. /me 같은 singleton path가 set 단계에서 그대로 emit되고 .env/.env.production이 같이 자동 생성. 4 generator의 표준 idiom이 다르면서 baseline 의미는 같은 결로 박힌 결.

테스트 결정성이 살아남았다. 4 generator 단위 테스트가 LLM 호출 없이 끝까지 돌고, mock runCommand 같은 외부 프로세스도 없다. .env / application.yml 파일이 디스크에 만들어지는 결만 검증. CLAUDE.md 섹션 4의 5초 미만 단위 테스트 결.

## 배운 점

ADR 0047이 ADR 0046의 healthcheck baseline에 의지한 결이 자연스러웠다. /health endpoint가 4 backend generator에 박혀 있으니 run.js의 readyUrl 표가 한 곳에 깔끔히 모였다. node→3000, java→8080, python→8000. 사용자가 어느 언어를 골라도 같은 결로 ready 안내를 본다. 두 ADR이 평행으로 자란 결.

spawnProcess 의존성 주입 결을 ADR 0022 verify의 runCommand 결로 그대로 옮긴 게 좋았다. 다만 run은 long-running이라 verify의 (cmd, args, cwd) → { exitCode, stdout, stderr } 결을 그대로 못 쓴다. 대신 onStdout/onStderr 콜백 + handle.kill() + handle.exited Promise 결로 확장. mock spawnProcess가 lifecycle을 통제할 수 있어 단위 테스트가 결정적으로 끝까지 돌았다.

mock spawnProcess의 결: `{ pid, kill, exited, _finishWithCode }`. _finishWithCode는 테스트가 직접 child 종료를 트리거할 때 쓰는 결로, "한쪽이 먼저 종료되면 다른 쪽도 정리" 시나리오를 결정적으로 검증한다. handle.killed로 cleanup이 호출됐는지 단언. lifecycle 통제 결이 mock 한 곳에 모이니 테스트가 한 결로 읽힌다.

readiness 폴링이 60초 default로 박혔지만 테스트는 readinessTimeoutMs=50ms로 줄여 timeout 시나리오를 빠르게 돈다. 결정성 결을 살리는 결로 인자가 풀렸다. forge/temper의 confirm 함수처럼 외부 I/O를 인자로 추출한 결과 같음.

AbortSignal로 Ctrl-C 결을 표현한 게 깔끔했다. bin/beoreum.js는 process.on('SIGINT')에서 ac.abort()를 호출하고, runRun은 signal.aborted를 감지해 두 child를 정리. 테스트는 `setTimeout(() => ac.abort(), 50)`로 시뮬레이션. 실제 signal 없이도 lifecycle 끝까지 검증.

prefix 결합 출력이 stdout/stderr 한 결로 박혔다. 표준 dev 서버(fastify, vite, spring-boot, uvicorn)가 보통 한 줄 단위로 출력하니 line-buffer가 자연스럽게 동작한다. flushBuf 헬퍼가 줄바꿈 단위로 끊어 onStdout 호출. 마지막 buffer 잔여분도 close 이벤트에서 flush.

Python의 backend 명령이 intent.yml의 what을 읽어 패키지 이름을 추출하는 결을 박았다. python.js generator의 buildProjectPackage 결을 그대로 run.js에 옮겼다. 두 곳에 같은 로직이 박힌 결인데 미래에 generator의 결이 바뀌면 run.js도 따라가야 한다는 결합도. 미래에 한 곳으로 모으는 정리 작업으로 미룬다.

target='invalid' 같은 잘못된 값에 한국어 에러로 안내. CLAUDE.md 섹션 8 사용자 출력 결("비기술 창업자가 결과 CLI 출력을 보고 무슨 일이 일어났는지 이해").

## 추천

## 알아둘 것

- runRun이 long-running이라 단위 테스트마다 setTimeout으로 abort하는 결이 박혀있다. 테스트가 잘못 짜이면 영원히 매달릴 위험이 있어 readinessTimeoutMs와 abort timer로 두 안전망. 미래에 새 시나리오 추가 시 같은 결을 따라가야 함
- defaultSpawnProcess가 `FORCE_COLOR: '0'` 환경 변수를 박는다. 컬러 escape 코드가 prefix 결합 출력을 흐리게 만들지 않게. 사용자가 컬러를 원하면 환경 변수로 override 가능
- handle.killed 플래그로 cleanup 호출을 single-shot으로 보호. SIGTERM 이후 SIGKILL이 들어와도 두 번째 호출은 무시. mock에서도 같은 결
- bin/beoreum.js의 SIGINT 핸들러가 process.off로 cleanup된다. 한 명령 안에서 등록한 핸들러가 명령 끝에 분리되는 결. 미래에 다른 long-running 명령(verify 스모크?)이 추가되면 같은 패턴
