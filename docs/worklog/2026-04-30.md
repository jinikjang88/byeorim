## 배운 점
- 카탈로그 추가는 코드가 아니라 데이터 작업이지만 데이터 결정에 매니페스토가 그대로 묻어난다. reservation cascade 첫 질문을 "두 손님이 동시에 마지막 자리를 잡으면"으로 둔 건 매니페스토 II.6의 한 줄을 데이터로 옮긴 자리. 미래에 카탈로그를 보는 사람이 매니페스토를 안 읽었어도 cascade 질문이 그 정신을 품는다
- "예약" 키워드가 추가되니 기존 두 테스트(ai-mock의 "알 수 없는 도메인"과 cli-prospect의 같은 자리)가 깨졌다. 둘 다 "우주여행 예약 시스템"이라는 입력으로 미지의 도메인을 흉내 냈는데 "예약" 단어가 reservation을 추천하게 됨. 키워드 표를 갱신할 때 그 키워드를 흉내 자리에 박아둔 다른 테스트가 있는지 점검해야 한다는 신호. 이번엔 두 자리만 잡혔지만 미래에 더 많은 도메인이 들어오면 같은 패턴이 반복될 가능성. CLAUDE.md 섹션 8의 "데이터 무관성"이 코드 본문에는 적용되어 있지만 테스트의 입력 문구에도 같은 결로 적용해야 한다는 작은 깨달음
- commerce와 reservation이 모두 W-money 자리(돈이 흐르는 세계)에 payment, refund를 두지만 commerce는 settlement까지, reservation은 deposit까지 둔다. 같은 슬러그(billing)를 두 도메인이 쓰면 미래 멀티모듈 emit 시 충돌 가능성. 이번 출시는 카탈로그가 한 번에 한 개만 활성화되므로 문제 없음. 미래에 멀티 도메인 합성이 들어오면 슬러그 충돌은 별도 ADR
- analogy 필드가 commerce와 reservation에는 있지만 job-aggregator에는 없다. 형식 차이가 두 번째로 굳어졌다. 이걸 통일할지는 별도 ADR 후보(2026-04-28 catalog-evolution 노트가 이미 같은 자리를 한 번 짚었다). 이번 PR에서는 통일하지 않음. 신규 카탈로그(reservation)는 commerce 결을 따른다는 결정만 명시

## 아직 열려있는 것
- 무료 예약 도메인(결제 없는 학원 첫 상담 같은 자리)이 cascade 질문으로만 분기됨. 무료 예약이 압도적인 도메인이라면 payment를 requires가 아니라 affects로 두는 게 맞을 수도 있음. 사용자 신호가 나오면 다시 본다. 이건 다이어리 후보
- 멀티 호스트(공유 사무실/공유 스튜디오) 도메인은 첫 출시에서 제외. 들어오면 settlement 블럭과 멀티 호스트 정산 흐름이 다시 필요. 별도 ADR 자리
- 노쇼 처리 옵션 중 "다음 예약 제한(블랙리스트)"은 사용자 데이터 보관과 권리 자리에 묶임. 절대 금지선 7번(텔레메트리 금지)과 결은 다르지만 한 번 더 검토 필요. cancellation-policy cascade의 두 번째 질문 결정 자리
- job-aggregator의 analogy 누락 상태가 두 번째 catalog-evolution 노트에서도 같은 자리를 짚게 됨. 카탈로그 형식 통일 ADR 후보. 이번 PR 범위 외
- 자체 적용(.byeorim/project/intent.yml 등)은 여전히 시작 안 됨. 다음 자리 후보. 이번 PR로 도메인 카탈로그가 세 개가 되어 자체 적용 시 더 풍부한 자리가 됨
